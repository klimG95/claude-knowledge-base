# AGENT-MANUAL — Playbook для Claude в claude-knowledge-base

Документ адресован LLM-агенту (Claude), а не человеку. Читается в любой нетривиальной сессии после установки пакета — указатель на него стоит в `obsidian-aura/AGENTS.md`. Цель — дать агенту полное понимание методологии: концепты, шаблоны, триггеры, паттерны кастомизации под конкретный проект, типовые воркфлоу, anti-patterns. Документ декларативный: таблицы, bullets, короткие абзацы, конкретные примеры. Narrative и мотивация — только там, где без них теряется суть.

## 1. Концепции

Этот раздел описывает фундамент методологии. Если в сессии действие непонятно или стандарт молчит — возвращайся сюда и действуй по аналогии с ближайшим разделом.

### 1.1. Три слоя памяти

Память агента распределена по трём слоям. Каждый слой имеет свою роль, свой носитель и свои правила обновления.

| Слой | Носитель | Что хранит | Когда читать | Когда писать |
|------|----------|------------|--------------|--------------|
| Семантический | `obsidian-aura/wiki/` + `index.md` | Знания о мире, концепции, факты, источники, связи | Перед содержательным ответом | После обработки `raw/` или новой темы |
| Процедурный | `obsidian-aura/AGENTS.md` | Правила работы, шаблоны процессов, триггеры | При старте сессии (автоматически в системный промпт) | Только через каскадный ADR |
| Эпизодический | Auto-memory в `~/.claude/projects/<project-id>/memory/` | Контекст про пользователя, указатели в vault, история сессий | При старте сессии (автоматически) | По триггеру «запомни» или в финальном sweep |

**Правила связки слоёв:**

1. Перед содержательным ответом порядок чтения: auto-memory → `index.md` → конкретные страницы wiki. Никогда не сканируй wiki целиком, никогда не отвечай «из головы», если в vault есть зафиксированный ответ.
2. После содержательной сессии обнови auto-memory указателем на новые ссылочные страницы (не дублируй содержание — только короткий указатель).
3. При расхождении между слоями приоритет за vault. Auto-memory — снимок на момент записи, vault — живой источник истины.
4. Когда пользователь говорит «запомни X» без уточнения — выбирай слой по сути X (см. таблицу в [§3.1](#31-стандартные-триггеры-пользователя)).

### 1.2. Источники истины: vault про «почему», код про «как сейчас»

Если в установке есть отдельный код-репозиторий проекта (например, `<repo>/` рядом с vault), действует жёсткое разделение:

- **Код** — единственный источник истины о том, как система работает прямо сейчас. Факт легко получить из кода → он не дублируется в vault.
- **Vault** — единственный источник истины о том, что мы решили, почему решили, какой контекст за этим стоял. Vault интерпретирует, обосновывает, связывает.

**Практическое следствие:** при сомнении «писать ли это в vault» спроси себя — переживёт ли этот факт следующее переписывание кода. Если нет (имя функции, текущая структура полей) — не пиши в vault, пиши ссылку на файл. Если да (мотивация выбора, контекст принятия решения, инвариант, который нельзя нарушать) — пиши страницу wiki.

### 1.3. MOC (Map of Content) — точка входа в проект

MOC — корневая страница проекта в vault. Это **не оглавление**, а карта-разводка с TL;DR, высокоуровневой архитектурой, и таблицами навигации «тип запроса → какие страницы открывать».

**Атрибуты MOC:**
- frontmatter `type: moc`;
- TL;DR в 3-6 строк: что это за проект, где код, какие компоненты, prod-окружение если есть;
- Mermaid высокоуровневой архитектуры — обязательно, если у проекта больше 3 компонентов;
- таблица «Быстрая навигация» (agent-friendly): тип запроса → страница для первого Read;
- разделы по типам артефактов (компоненты, контракты, инциденты, runbook'и, ADR, domain hubs, inventory).

**Имя файла:** `<project>.md` (kebab-case латиницей). Например `<project>.md`, не `проект-x.md`.

### 1.4. ADR (Architecture Decision Record) — долговременная память решений

ADR фиксирует нетривиальное решение так, чтобы пережить несколько переписываний кода. Имя: `wiki/adr-NNN-short-name.md`, где `NNN` — последовательный трёхзначный номер.

**Когда создавать ADR:**
- Архитектурное решение, влияющее на структуру системы.
- Каскадное изменение методологии (новый формат страниц, смена конвенции, реорганизация разделов).
- Выбор между технологическими опциями (репо, фреймворк, протокол).

**Когда НЕ создавать ADR:**
- Точечная правка одной-трёх страниц.
- Багфикс без архитектурного выбора.
- Эксперимент, не закрепляемый как решение.

**Структура ADR** — см. шаблон [§2.2](#22-template-adr).

### 1.5. Runbook — операционные процедуры

Runbook — пошаговая операционная процедура в формате «предусловия → шаги → проверка → откат». Имя: `wiki/runbook-<name>.md`.

**Когда создавать runbook:**
- Процедура выполняется регулярно или редко, но с риском ошибки.
- Процедура нетривиальна (>3 шагов с условиями).
- Нужно восстановление контекста между сессиями (как делали в прошлый раз).

**Атрибут `automation_status`** в frontmatter определяет степень автоматизации: `manual` (всё руками), `semi-auto` (часть скриптами), `automated` (запускается одной командой). Поле `last_executed` обновляется после фактического выполнения.

### 1.6. Incident-log — журнал инцидентов

Incident-log — единая страница типа `<project>-incidents-log.md` с разделами по инцидентам. Каждый раздел — отдельный инцидент по структуре [§2.3](#23-template-incident).

**Принцип:** инциденты собираются в один файл, не в отдельные. Отдельный файл создаётся только если инцидент стал ссылочным эталоном — на него ссылаются другие страницы по имени.

**Ценность incident-log не в фиксации факта**, а в секции `Prevention` — правила, выведенные из инцидента, которые превращаются в обязательные проверки или дополнения других страниц.

### 1.7. Inventory-страницы — карты-указатели по типам артефактов

Inventory-страница — реестр артефактов одного типа в формате «артефакт ↔ путь в коде ↔ страница vault». Назначение — дать агенту общий обзор без многих Read'ов.

**Типичные inventory:**

| Имя | Содержимое |
|-----|------------|
| `<project>-inventory-code` | Компонент ↔ путь в репо ↔ страница vault |
| `<project>-inventory-endpoints` | Все HTTP endpoints + IPC commands |
| `<project>-inventory-configs` | Config-файлы + env vars |
| `<project>-inventory-tests` | Тесты и что покрывают |
| `<project>-inventory-state` | Где хранится состояние (DB, files, in-memory) |

Frontmatter: `type: concept`, `shape: inventory`, `layer: concept`, `component: cross`.

Шаблон — см. [§2.10](#210-template-inventory).

### 1.8. Domain hubs — навигаторы cross-cutting доменов

Domain hub — mini-MOC для сквозного домена, проходящего через несколько компонентов. Имя: `<project>-cross-<domain>.md`.

**Типичные домены:**
- `<project>-cross-logging` — логирование (producer → transport → storage → consumer).
- `<project>-cross-auth` — аутентификация (клиент → сервер → DB → admin).
- `<project>-cross-packaging` — упаковка/деплой (build → distribution → install → update).
- `<project>-cross-telemetry` — телеметрия.
- `<project>-cross-licensing` — лицензирование.

**Состав:** TL;DR + Mermaid `sequenceDiagram` end-to-end + таблица «Участники» (компонент → роль → страница) + анти-паттерны на стыках компонентов.

Шаблон — см. [§2.9](#29-template-domain-hub).

### 1.9. Reading map — таблица «ситуация → страницы»

Reading map — таблица в формате «тип запроса / ситуация → какие страницы открывать в первую очередь». Живёт в двух местах:

1. **В MOC проекта** — раздел «Быстрая навигация» для запросов по проекту.
2. **В `AGENTS.md` репо кода** (если у проекта есть отдельный `<repo>/AGENTS.md`) — раздел «Reading map» для агента, запущенного в репо кода.

**Пример** (универсальный):

| Ситуация | Открыть |
|----------|---------|
| Изменение core-логики | `<project>-<core-module>`, `<project>-invariants` |
| Добавление HTTP endpoint | `<project>-inventory-endpoints`, `<project>-server-routes`, `<project>-contract-<api>` |
| Инцидент в домене X | `<project>-cross-<X>`, `<project>-incidents-log` |
| Изменение пакета/деплоя | `<project>-cross-packaging` |

Reading map наполняется по мере проявления типовых запросов, не выдумывается заранее.

## 2. Шаблоны страниц

Все шаблоны живут в `obsidian-aura/wiki/templates/`. Использование: копируешь шаблон, заполняешь, удаляешь неиспользуемые секции. Шаблоны эволюционируют — задним числом их изменения применяются к существующим страницам **только** через каскадный ADR (см. [§3.4](#34-каскадные-изменения-методологии)).

### 2.1. Когда какой шаблон применять — decision-tree

```
Это решение?
├── Да → template-adr (§2.2)
└── Нет
    │
    Это операционная процедура?
    ├── Да → template-runbook (§2.4)
    └── Нет
        │
        Это инцидент?
        ├── Да → template-incident (§2.3), как раздел в incidents-log
        └── Нет
            │
            Это страница про компонент / модуль кода?
            ├── Богатая логика, инварианты, контракты → template-component (§2.6)
            ├── Мелкий модуль (utils, helpers) → template-reference (§2.7)
            └── API / IPC / wire-формат → template-contract (§2.8)
            │
            Это навигатор?
            ├── Сквозной домен через компоненты → template-domain-hub (§2.9)
            ├── Реестр артефактов одного типа → template-inventory (§2.10)
            └── Корневой MOC проекта → ручная разводка без шаблона
            │
            Недельный обзор по journal/ → template-weekly-review (§2.5)
```

### 2.2. template-adr (ADR)

Шаблон: `wiki/templates/template-adr.md`.

**Frontmatter:**
```yaml
---
type: adr
adr_id: <NNN>
status: proposed | accepted | superseded | deprecated
tags: [methodology, architecture]
created: YYYY-MM-DD
updated: YYYY-MM-DD
# superseded_by: "[[adr-MMM-...]]"   # только если superseded
---
```

**Секции:**

| Секция | Назначение | Обязательность |
|--------|------------|----------------|
| Context | Что было известно перед решением, ограничения, потребность. 2–6 строк, без воды | да |
| Considered options | 2–4 альтернативы с плюсами и минусами каждой | да |
| Pre-flight checks | Чек-лист перед операцией: затронутые файлы, dry-run критических действий, зависимости от внешних состояний, формулировка отката | для каскадных и для операций над файловой системой |
| Decision | Что выбрано и почему. Одно-два предложения с ссылкой на сильнейший аргумент | да |
| Migration plan | План каскадной миграции: затронутые файлы, характер правок, атомарность, проверки | для каскадных ADR |
| Verify | Чек-лист после выполнения | для решений с активными действиями |
| Consequences | Положительные, цена (что отдаём), follow-ups | да |
| Связано с | Двусторонние `[[ссылки]]` | да |
| Источник | Откуда контекст — сессия, briefing, журнал | да |

**Пример заполнения секции Pre-flight (обязательная страховка):**

```markdown
## Pre-flight checks

- [x] Затронутые файлы перечислены полно (grep по vault на старые имена / пути).
- [x] Критическая операция протестирована dry-run.
- [x] Зависимости от внешних состояний выявлены (открытые сессии IDE, активные процессы, file locks).
- [x] Откат сформулирован и реалистичен (`git revert` или явная обратная команда).
```

### 2.3. template-incident (Incident)

Шаблон: `wiki/templates/template-incident.md`. Используется как раздел в incidents-log, не отдельным файлом (кроме случаев ссылочного эталона).

**Мини-frontmatter в начале раздела** (не YAML-блок, а строки текста):
```markdown
**Status:** open | resolved | recurring
**Severity:** S1 (полный отказ) | S2 (частичная деградация) | S3 (cosmetics)
```

**Секции:**

| Секция | Назначение |
|--------|------------|
| Symptom | Что наблюдалось глазами пользователя/тестировщика. Без интерпретации |
| Misdiagnosis (опц.) | Ложные гипотезы и почему отвергнуты — сохраняет урок «не идти по этому пути» |
| Root cause | Реальная причина. Конкретно: модуль, строка, условие |
| Fix | Что сделано. Если фикс не выкачен — отметить состояние |
| Prevention | Правила, проверки, тесты, выведенные из инцидента. Самая ценная секция |
| Связано с | Компоненты/темы, к которым относится |

**Принцип:** `Prevention` — это перевод инцидента в долговременное знание. Если после записи инцидента эту секцию некуда зафиксировать в виде правила (дополнение страницы компонента, инвариант, runbook) — инцидент пока не «отработан».

### 2.4. template-runbook (Runbook)

Шаблон: `wiki/templates/template-runbook.md`.

**Frontmatter:**
```yaml
---
type: runbook
automation_status: manual | semi-auto | automated
tags: [operations]
created: YYYY-MM-DD
updated: YYYY-MM-DD
# last_executed: YYYY-MM-DD   # после первого выполнения
---
```

**Секции:**

| Секция | Назначение |
|--------|------------|
| Prerequisites | Условия выполнения процедуры |
| Procedure | Шаги с командами как они есть. Без объяснений между блоками, если шаг не требует ручного решения |
| Verification | Smoke-check после процедуры: команда → ожидаемый ответ |
| Rollback | Конкретная процедура отката, либо явное «откат невозможен» |
| What NOT to do | Соблазны «заодно сделать X» и почему этого нельзя в этой процедуре |
| Связано с | ADR/инциденты, породившие runbook |

### 2.5. template-weekly-review (Weekly review)

Шаблон: `wiki/templates/template-weekly-review.md`. Имя файла: `journal/YYYY-WNN-review.md` (где `WNN` — номер недели).

**Секции:** Сессии (список со ссылками на `journal/YYYY-MM-DD`) → Изменения в vault → Принятые решения → Инциденты → Открытые нити → На следующую неделю.

Создаётся по триггеру «сделай weekly review» или в финальном sweep последней сессии недели.

### 2.6. template-component (Concept shape)

Шаблон: `wiki/templates/template-component.md`. Применяется для подсистем с богатой логикой: инварианты, контракты, нетривиальная архитектура.

**Frontmatter (расширенный — см. [§4.6](#46-расширения-frontmatter-под-проект)):**
```yaml
---
type: concept
tags: [<project>, <component>, <layer>]
component: <component-name>
layer: kernel | integration | ui | ops | contract | concept
shape: concept
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

**Секции:**

| Секция | Назначение |
|--------|------------|
| TL;DR | 3–5 строк: что это, ключевая идея, где код, кому/когда полезна страница |
| Когда читать эту страницу | Список типовых ситуаций — для agent-first сценария |
| Идея | 1–2 абзаца: зачем существует, какую проблему решает, какое место в системе занимает |
| Инварианты | Что нельзя нарушать. Привязка к глобальной странице инвариантов |
| Реализация | Таблица «подмодуль → файл → ключевые функции/классы» + Mermaid если поток нетривиален |
| Контракты | Что входит/выходит. Если контракт большой — TL;DR + ссылка на отдельную contract-страницу |
| Зависимости | Внутренние (другие подсистемы), внешние библиотеки, внешние сервисы |
| Анти-паттерны / gotchas | Что часто ломают, ссылки на инциденты |
| Связано с | Минимум 5 двусторонних `[[...]]` |
| Источник | Файлы кода, ТЗ, ADR, briefing, auto-memory |

### 2.7. template-reference (Reference shape)

Шаблон: `wiki/templates/template-reference.md`. Для мелких модулей (utils, state, tools) без богатой логики.

**Секции:** TL;DR (2–3 строки) → Когда читать → Что делает (bullets, не narrative) → Где код (таблица файл → назначение) → Связано (минимум 3 связи) → Источник.

**Решающее различие component vs reference:**
- Если у модуля есть инварианты, контракты, нетривиальные зависимости → component.
- Если модуль — набор утилит без сложных правил → reference.

### 2.8. template-contract (Contract shape)

Шаблон: `wiki/templates/template-contract.md`. Для API, IPC, wire-форматов.

**Секции:** TL;DR (между кем, версия) → Когда читать → Поля/методы (таблица имя/тип/назначение/обязательность) → Пример запроса/ответа (JSON) → Версионирование и совместимость → Использующие стороны (producer/consumer/spec) → Связано → Источник.

**Принцип:** spec-файл (OpenAPI/JSON Schema/protobuf) — источник истины о форме. Страница vault — источник истины о мотивации, инвариантах, совместимости.

### 2.9. template-domain-hub

Шаблон: `wiki/templates/template-domain-hub.md`. Для сквозных доменов (logging, auth, packaging, telemetry, licensing и т.п.).

**Секции:** TL;DR (в каких компонентах живёт) → Когда читать → End-to-end flow (Mermaid `sequenceDiagram` обязателен) → Участники (таблица компонент/роль/страница) → Ключевые контракты → Анти-паттерны сквозные → Связано (минимум 5) → Источник.

**Принцип:** domain-hub — не дубль страниц компонентов, а навигатор. Подробности живут на страницах компонентов, hub только связывает.

### 2.10. template-inventory

Шаблон: `wiki/templates/template-inventory.md`. Для реестров артефактов.

**Секции:** TL;DR (для какого типа артефактов) → Когда читать → Реестр (таблица артефакт/путь/страница/доп. поле) → Принцип организации → Связано → Источник.

**Принцип:** inventory обновляется при добавлении/удалении артефакта типа. Если артефактов мало (<5) — таблица в страницу компонента, отдельная inventory не нужна.

## 3. Триггеры и автономность

Базовое поведение — действовать самостоятельно по стандарту, не спрашивая разрешения на стандартные операции. Если правила требуют уточнения — это сигнал дополнить `AGENTS.md`, а не оседать на разовых договорённостях.

### 3.1. Стандартные триггеры пользователя

| Триггер (фраза пользователя) | Стандартное действие | Ссылка на процесс |
|------------------------------|-----------------------|--------------------|
| «обработай raw» / «обработай новый файл» | Capture → organize → distill → express: чтение целиком, выделение сущностей, страницы wiki с двусторонними ссылками, маркер `<!-- processed: YYYY-MM-DD -->`, обновление `index.md`, запись в `CHANGELOG.md` | [§5.1](#51-обработка-raw-материалов) |
| «сохрани X» / «запомни X» / «зафиксируй» | Выбор слоя по сути X (см. таблицу ниже) | [§1.1](#11-три-слоя-памяти) |
| «закрой сессию» / «закрой спринт» / «подведём итоги» | Финальный sweep: index + journal + CHANGELOG + auto-memory + проверка ссылочной целостности | [§5.5](#55-закрытие-сессии) |
| «зафиксируй решение» / «архитектурно так» | Создать ADR по [§2.2](#22-template-adr), имя `wiki/adr-NNN-short-name.md` | [§5.2](#52-создание-обновление-adr) |
| «зафиксируй инцидент» / «у нас инцидент» | Добавить раздел в `<project>-incidents-log.md` по [§2.3](#23-template-incident) | [§5.3](#53-запись-инцидента) |
| «сделай runbook для X» | Новая страница `wiki/runbook-X.md` по [§2.4](#24-template-runbook), ссылка из MOC | [§5.4](#54-создание-runbook) |
| «измени Y в методологии» / «теперь будем делать иначе» | Каскадный процесс: ADR с Migration plan + миграция | [§3.4](#34-каскадные-изменения-методологии) |
| «проверь всё» / «ревизия» / «аудит» | Системная проверка: Glob + Grep на битые ссылки + сверка с index + проверка auto-memory | [§5.6](#56-ревизия-и-аудит-методологии) |

**Выбор слоя памяти для «сохрани X»:**

| Природа X | Слой | Куда |
|-----------|------|------|
| Знание о мире (факт, концепция, источник) | Семантический | Страница wiki по обычным правилам |
| Правило поведения агента / методологическое | Процедурный | `AGENTS.md` или auto-memory `feedback` |
| Предпочтение пользователя | Эпизодический | Auto-memory `user` |
| Текущий контекст работы (что в работе, к чему вернуться) | Эпизодический | Auto-memory `project` |
| Ссылочный артефакт (где живёт X, кто эталон) | Эпизодический | Auto-memory `reference` (короткий указатель) |

### 3.2. Когда действовать, когда спрашивать

| Ситуация | Действие |
|----------|----------|
| Триггер однозначно соответствует стандарту | Действовать без вопросов |
| Триггер неоднозначен, действие обратимое в рамках задачи | Действовать, объяснив выбор в одну-две строки в конце ответа |
| Действие необратимое (commit/push/удаление файла, изменения вне vault) и не было явно запрошено | Спросить |
| Триггер выходит за рамки vault (прямые правки кода в репо без явной просьбы) | Спросить. Исключение — правка `<repo>/AGENTS.md`, явно делегированная конституцией |
| Стандарт молчит | Действие по аналогии с близким разделом + в той же сессии предложить дополнение `AGENTS.md` |

**Жёсткое правило:** не задавать вопросы вида «куда сохранить?», «какой это слой?», «делать ли journal?» — стандарт это определяет.

### 3.3. Параметры frontmatter и обновление `updated`

**Минимальное ядро для всех страниц `wiki/` и `journal/`:**

```yaml
---
type: <см. список>
tags: [tag1, tag2, ...]
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

**Значения `type`:** `concept` / `entity` / `source` / `adr` / `runbook` / `incident-log` / `moc` / `template` / `system` / `journal`.

**Расширения по типам:**

| Type | Дополнительные поля |
|------|---------------------|
| `adr` | `adr_id: <int>`, `status: proposed\|accepted\|superseded\|deprecated`, опц. `superseded_by: "[[adr-...]]"` |
| `runbook` | `automation_status: manual\|semi-auto\|automated`, опц. `last_executed: YYYY-MM-DD` |
| `source` | `source_type: article\|book\|video\|podcast\|repo\|web-research\|api-doc`, опц. `source_url` |
| `entity` | `entity_kind: model\|product\|plugin\|tool\|person\|org` |

**Стандартные теги** (используй применимые из набора): `claude`, `prompt-engineering`, `obsidian`, `vscode`, `mcp`, `second-brain`, `methodology`, `architecture`, `operations`, `infrastructure`, `risk`, `template`, `journal`. Плюс тег с именем проекта (например `<project>`).

**Обновление `updated`:**
- При **значимой** правке (содержательное изменение, не косметика) обновляй `updated: YYYY-MM-DD`.
- Не обновляй при тривиальной правке (опечатка, выравнивание).
- Граница субъективна → в сомнительном случае предпочитай обновлять.

### 3.4. Каскадные изменения методологии

Каскадное изменение — затрагивающее структуру или содержимое многих файлов одновременно. Триггеры:
- Изменение `AGENTS.md` с новыми правилами формата.
- Смена конвенции именования файлов или папок.
- Введение нового обязательного поля или секции.
- Изменение шаблона, которое должно быть применено к существующим страницам того же жанра.
- Реорганизация разделов `index.md`.

**Принципы выполнения каскада:**

| Принцип | Конкретика |
|---------|------------|
| Отдельная сессия | Не смешивается с содержательной работой по проекту |
| Оформляется как ADR | Создаётся `wiki/adr-NNN-...` со статусом `proposed` и обязательной секцией `Migration plan` |
| Атомарность | За одну сессию если файлов <30. Больше — этапами с явным migration window |
| Проверки перед закрытием | Ссылочная целостность, `index.md` отражает новое состояние, все целевые файлы обновлены |
| Запись | В `CHANGELOG.md` короткий пункт со ссылкой на ADR, в `journal/` детальная запись |
| Откат | Через `git revert` коммита каскада, не ручное обратное переписывание |

**Когда каскад не нужен:** правка 1–3 страниц — обычная правка, ADR не требуется. Граница субъективна → в сомнительном случае предпочесть ADR.

## 4. Кастомизация под проект

Главный раздел манyala. Описывает, как агенту обустроить vault под конкретный проект пользователя. Содержит универсальные правила и паттерны, проверенные на крупных кодовых базах.

### 4.1. Bootstrap: первая сессия после установки

В первой сессии после `install.ps1` агент работает по сценарию из `BOOTSTRAP.md`. Базовая последовательность:

1. **Понять проект.** Через диалог: тип проекта (web/mobile/CLI/library/data), репо (если есть), стек, размер команды, текущий статус (greenfield / brownfield).
2. **Уточнить оптику.** Agent-first vs human-first ([§4.3](#43-решение-про-оптику-agent-first-vs-human-first)).
3. **Создать project MOC.** Файл `wiki/<project>.md` ([§4.2](#42-создание-project-moc)).
4. **Дописать раздел проекта в `AGENTS.md`.** Указатель на MOC + ключевые специфичные правила.
5. **Заполнить auto-memory** ([§4.8](#48-auto-memory-под-нового-пользователя)).
6. **Зафиксировать решение по структуре vault как ADR-001** проекта.
7. **Финальный sweep.** `index.md`, `journal/YYYY-MM-DD.md`, `CHANGELOG.md`.

**Что НЕ делать в bootstrap:**
- Не создавать сразу полную структуру по всем компонентам — это работа на 5+ сессий, не bootstrap.
- Не задавать вопросы, ответы на которые однозначны по стандарту (язык общения, формат записей, нужно ли journal).
- Не создавать файлы до согласования общей картины с пользователем (план в чате, потом файлы).

### 4.2. Создание project MOC (Map of Content)

**Минимальный MOC** (для bootstrap):

```markdown
---
type: moc
tags: [<project>, architecture]
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# <Project> (MOC)

**TL;DR.** <Описание проекта в 2–4 строки: что делает, где код, статус>.

## Высокоуровневая архитектура

(Mermaid если >3 компонентов, иначе bullets.)

## Компоненты

(Таблица или список — будет наполняться по мере исследования.)

## ADR

- [[adr-001-<project>-vault-structure]] — структура vault для проекта

## Открытые нити

(То, что осталось проработать в следующих сессиях.)

## Связано с

- [[methodology-overview]]

## Источник

Создан в bootstrap-сессии YYYY-MM-DD.
```

**Расширения по мере роста:** Быстрая навигация → Контракты → Domain hubs → Inventory → Runbook'и → Инциденты → Tech debt.

### 4.3. Решение про оптику: agent-first vs human-first

**Agent-first vault** оптимизирован под чтение LLM-агентом. Признаки:
- Декларативные блоки вместо narrative.
- TL;DR в начале каждой страницы.
- Inline-ссылки на код относительными путями.
- Жёсткие шаблоны (component/reference/contract/domain-hub/inventory).
- Плотные `[[wikilinks]]` для графа.
- Inventory-страницы для общих обзоров (заменяют сканирование).
- Анти-паттерны явной секцией.

**Human-first vault** оптимизирован под чтение человеком. Признаки:
- Свободная narrative-структура.
- Подробные мотивации, истории, объяснения.
- Меньше шаблонной унификации.
- Меньше inventory — больше «общих заметок».

**Когда выбирать agent-first:** проект с активной AI-командой, частыми сессиями Claude, потребностью в reproducibility между сессиями. **Большинство проектов в этом пакете — agent-first**.

**Когда выбирать human-first:** vault больше для личных заметок, чем для операционной работы; пользователь часто читает страницы вручную; нет необходимости в систематической работе агентов.

**Гибрид допустим:** базовая методология (3 слоя, ADR/runbook/incident) одинакова, оптика варьируется по разделам. Например — wiki общих знаний human-first, страницы проекта agent-first.

Решение про оптику принимается на bootstrap и фиксируется в ADR-001 проекта.

### 4.4. Выбор оси организации страниц

Три варианта структуры project-страниц в `wiki/`:

| Вариант | Описание | Плюсы | Минусы |
|---------|----------|-------|--------|
| **A. Зеркало кода** | Иерархия повторяет структуру репо. `<project>-bot-core`, `<project>-bot-mt5`, ... | Очевидное соответствие, хорошо параллелится | Сквозные домены (logging, auth) приходится собирать вручную |
| **B. По доменам** | Группировка по ответственности: `<project>-licensing`, `<project>-logging`, ... | Cross-cutting явный | Не совпадает с репо, хуже параллелится |
| **C. Гибрид** | Скелет = A (зеркало кода), поверх 3–5 cross-cutting доменных хабов из B | Обе оси навигации работают | Чуть больше страниц, требует дисциплины |

**Рекомендация:** для проекта с >5 компонентов и >2 сквозными доменами — гибрид C. Для маленького проекта — простое зеркало кода A.

### 4.5. Структурная документация по паттерну «skeleton + waves»

Применяется для проектов с >5 компонентами и подсистемами. Это паттерн полной структурной документации, проверенный на крупных кодовых базах.

**Когда применять:**
- Проект уже «вырос» — есть код, есть docs, есть briefing, но в vault только верхний уровень.
- Команда работает агентами, нужна навигация для агента, а не для человека.
- Vault станет операционной средой работы.

**Когда НЕ применять:**
- Проект меньше 5 компонентов → простая структура без skeleton.
- Проект greenfield, реальной системы ещё нет → отложить до появления кода.
- Нет ресурса на 3–5 сессий наполнения → не начинать (плохо: создать skeleton и бросить с плейсхолдерами).

**5 типов страниц** (shape):

| Shape | Когда | Шаблон |
|-------|-------|--------|
| `concept` | Подсистемы с богатой логикой | [§2.6 template-component](#26-template-component-concept-shape) |
| `reference` | Мелкие модули, utils | [§2.7 template-reference](#27-template-reference-reference-shape) |
| `contract` | API / IPC / wire-форматы | [§2.8 template-contract](#28-template-contract-contract-shape) |
| `domain-hub` | Cross-cutting домены | [§2.9 template-domain-hub](#29-template-domain-hub) |
| `inventory` | Карты-указатели по типам артефактов | [§2.10 template-inventory](#210-template-inventory) |

**Процесс — skeleton + waves:**

1. **Skeleton-проход** (1 сессия, однопоточно):
   - Создать ADR с планом структуры (структура иерархии + список ~N страниц + waves).
   - Обновить MOC проекта.
   - Создать 5 sub-templates (если расширение оси: см. [§4.6](#46-расширения-frontmatter-под-проект)).
   - Создать N skeleton-страниц по шаблонам с плейсхолдерами `_TBD в волне N_`.
   - Обновить hub-страницы ссылками на подстраницы.
   - Обновить `index.md` со всеми новыми страницами.
   - Добавить раздел «Reading map» (skeleton) в `<repo>/AGENTS.md` если есть.

2. **Waves наполнения** (3–5 сессий по 1 волне):
   - Каждая волна — непересекающийся набор страниц (например, по компонентам).
   - В волне можно использовать параллельных агентов ([§5.7](#57-параллельные-агенты-на-больших-задачах)).
   - После каждой волны — reviewer pass: проверка Verify-критериев из ADR.

3. **Finalization** (последняя сессия):
   - Дополнить Reading map по реально проявившимся типовым запросам.
   - Обновить auto-memory указателями на ключевые inventory-страницы.
   - Финальный аудит ссылочной целостности.

**Жёсткое правило:** один файл — один агент в волне. Hub-страницы обновляет только главный агент / reviewer (race condition).

### 4.6. Расширения frontmatter под проект

Базовое ядро ([§3.3](#33-параметры-frontmatter-и-обновление-updated)) едино для всех проектов. Под конкретный проект можно расширять frontmatter дополнительными полями для Dataview-фильтрации.

**Типичные опциональные поля** (по паттерну skeleton+waves):

```yaml
---
type: concept
tags: [<project>, <component>, <layer>, <domain>]
component: <component-name>             # имя hub-компонента
layer: kernel | integration | ui | ops | contract | concept
shape: concept | reference | contract | domain-hub | inventory
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

**Правила введения опциональных полей:**
- Не пересекаются с `type` (который остаётся по стандарту).
- Введение фиксируется в ADR проекта (типа «расширение frontmatter под `<project>`»).
- Dataview-запросы используют расширенные поля для фильтрации.

**Анти-паттерн:** менять смысл значений `type` под проект. Это ломает кросс-проектные Dataview-запросы и `methodology-overview`.

### 4.7. Reading map в репо проекта

Если у проекта есть отдельный код-репозиторий с `<repo>/AGENTS.md`, в эту конституцию добавляется раздел **Reading map** — таблица «ситуация → какие страницы vault открывать в первую очередь».

**Когда добавлять:**
- Репозиторий проекта живёт в git, есть `<repo>/AGENTS.md` (своя конституция кода).
- Агент часто запускается из репо, а не из vault.
- Vault структурирован по паттерну skeleton + waves, есть >10 страниц проекта.

**Структура раздела:**

```markdown
## Reading map (vault navigation for this repo)

| Ситуация | Открыть в vault |
|----------|------------------|
| Изменение `<core-module>` | `<project>-<core-module>`, `<project>-invariants` |
| Добавление HTTP endpoint | `<project>-inventory-endpoints`, `<project>-server-routes`, `<project>-contract-<api>` |
| Инцидент с `<domain>` | `<project>-cross-<domain>`, `<project>-incidents-log` |
| Изменение пакета | `<project>-cross-packaging` |
| (Расширяется по мере проявления типовых запросов) | ... |
```

**Принцип:** Reading map наполняется по мере проявления реальных запросов, не выдумывается заранее.

### 4.8. Auto-memory под нового пользователя

Auto-memory живёт в `~/.claude/projects/<project-id>/memory/`. Стартовые шаблоны — в `auto-memory-templates/` пакета.

**Типы записей в auto-memory:**

| Префикс файла | Содержимое | Примеры |
|----------------|------------|---------|
| `user_*` | Стабильные предпочтения пользователя | `user_language.md`, `user_role.md` |
| `feedback_*` | Правила поведения, выведенные из обратной связи | `feedback_technical_autonomy.md`, `feedback_confirm_before_mutations.md` |
| `project_*` | Контекст проекта (что в работе, к чему вернуться) | `project_<name>_context.md` |
| `reference_*` | Указатели «где живёт X» | `reference_<repo>_path.md`, `reference_log_ops.md` |

**Принципы auto-memory:**

1. **Auto-memory — указатели, не копия.** Никогда не дублирует содержание vault. Запись типа «по теме X эталонная страница — `[[page-x]]`».
2. **Файл MEMORY.md — индекс auto-memory** со ссылками на все memory-файлы.
3. **При расхождении с vault приоритет за vault.** Если запись устарела относительно vault — обновить запись на указатель.
4. **Не накапливать.** Старые записи, переехавшие в vault, заменяются короткими указателями. Удалять можно — auto-memory не священная история, только рабочий контекст.

**Старт под нового пользователя (из bootstrap):**

1. Скопировать в auto-memory шаблоны: `user_language.md.example` → `user_language.md` и т.п.
2. Адаптировать содержание по результатам диалога bootstrap (язык, роль, автономность).
3. Создать `MEMORY.md` со списком файлов и одной строкой описания каждого.
4. Создать `project_<name>_context.md` с короткой картой проекта и ссылкой на MOC.

См. также `docs/customization.md#auto-memory`.

## 5. Воркфлоу

### 5.1. Обработка raw/ материалов

Триггер: «обработай raw», «обработай новый файл», «обработай всё новое».

**Цикл capture → organize → distill → express:**

1. **Capture.** Файл уже в `raw/` — это сделал пользователь.
2. **Organize.** Прочитать файл целиком (не по фрагментам). Выделить отдельные сущности и идеи.
3. **Distill.** Для каждой сущности:
   - Найти существующую страницу в `wiki/` (через `index.md` и Glob).
   - Если есть — обновить, добавив новый аспект / источник / связь.
   - Если нет — создать новую страницу по [§2](#2-шаблоны-страниц) с frontmatter.
4. **Express.** Простроить двусторонние ссылки: A → B и B → A.

**После обработки:**
- Добавить в начало файла в `raw/` маркер `<!-- processed: YYYY-MM-DD -->`. Если маркер уже есть — обновить дату.
- Исходный файл в `raw/` **никогда не удаляется и не переименовывается**.
- Обновить `index.md` под изменения в `wiki/`.
- Запись в `CHANGELOG.md` короткой строкой со списком затронутых страниц.

См. также `docs/workflows.md#raw-processing`.

### 5.2. Создание и обновление ADR

Триггер: «зафиксируй решение», «это решение», «архитектурно так».

**Создание нового ADR:**

1. Определить следующий свободный `NNN` (`Glob wiki/adr-*.md`, найти max).
2. Скопировать `templates/template-adr.md` → `wiki/adr-NNN-<short-name>.md`.
3. Заполнить frontmatter (`adr_id`, `status: proposed`, `created`, `updated`).
4. Заполнить Context → Considered options → Decision (минимум).
5. Если решение каскадное или с операциями над файловой системой — обязательно Pre-flight checks и Migration plan.
6. После выполнения решения — `status: accepted`, заполнить Consequences и Verify.
7. Добавить страницу в MOC проекта в раздел ADR и в `index.md`.

**Обновление ADR при изменении решения:**
- Если решение полностью пересматривается — новый ADR с `status: proposed`, который ссылается на старый. Старый получает `status: superseded`, `superseded_by: "[[adr-MMM-...]]"`.
- Если уточнение в рамках того же решения — правка в существующем ADR + обновление `updated`.

### 5.3. Запись инцидента

Триггер: «зафиксируй инцидент», «у нас инцидент».

1. Открыть `wiki/<project>-incidents-log.md` (создать если нет — frontmatter `type: incident-log`).
2. Добавить новый раздел сверху (новые инциденты — сверху, старые — снизу) по [§2.3](#23-template-incident).
3. Заполнить минимум: Status, Severity, Symptom. Остальное — по мере диагностики.
4. После resolve — заполнить Root cause, Fix, **обязательно Prevention**.
5. Связать с компонентами через `## Связано с`.
6. Если Prevention требует изменения страницы компонента или нового runbook — выполнить в той же сессии или явно открыть как follow-up в журнале.

**Когда инцидент → отдельный файл:** становится ссылочным эталоном (на него ссылаются 3+ другие страницы), либо имеет долгий поэтапный fix. Тогда `wiki/incident-<name>.md` с frontmatter `type: incident-log` или `type: concept`.

### 5.4. Создание runbook

Триггер: «сделай runbook для X».

1. Скопировать `templates/template-runbook.md` → `wiki/runbook-<name>.md`.
2. Заполнить Prerequisites → Procedure → Verification → Rollback → What NOT to do.
3. `automation_status` в frontmatter ставить честно: `manual` если все шаги руками, `semi-auto` если есть скрипты, `automated` если запускается одной командой.
4. Добавить ссылку из MOC проекта в раздел Runbook'и и из `index.md`.
5. После первого реального выполнения — обновить `last_executed: YYYY-MM-DD` и подправить шаги, если в реале что-то отличалось.

### 5.5. Закрытие сессии

Триггер: «закрой сессию», «закрой спринт», «зафиксируй сделанное», «подведём итоги».

**Финальный sweep (последовательность):**

1. **`index.md`** — обновлён, если в `wiki/` что-то менялось. Новые страницы добавлены в соответствующие разделы (Темы / Сущности / Источники).
2. **`journal/YYYY-MM-DD.md`** — создать (если первая сессия дня) или дополнить (если сессия продолжается). Содержимое:
   - Что делали (по пунктам).
   - К чему пришли.
   - Что осталось открытым (для следующей сессии).
   - Ссылки на затронутые страницы.
3. **`CHANGELOG.md`** — короткая запись сверху:
   ```markdown
   ## YYYY-MM-DD
   - Обработано: `raw/<file1>`, `raw/<file2>`.
   - Созданы: [[page-a]], [[page-b]].
   - Обновлены: [[page-c]].
   - Принято решение: [[adr-NNN-...]].
   ```
4. **Auto-memory** — обновлены указатели, если появились новые ссылочные эталоны. Принцип: «по теме X эталонная страница — `[[page-x]]`».
5. **Битые `[[ссылки]]`** — Grep по vault на имена удалённых/переименованных страниц. Все найденные битые ссылки исправить или сознательно оставить с пометкой (если ссылка на ещё не созданную страницу).

См. также `docs/workflows.md#session-close`.

### 5.6. Ревизия и аудит методологии

Триггер: «проверь всё», «ревизия», «аудит методологии».

**Системная проверка:**

1. **Полнота индекса.** Glob по `obsidian-aura/wiki/`, сверить с `index.md`. Найти orphan-страницы (есть в wiki, нет в index).
2. **Ссылочная целостность.** Grep всех `[[wikilink]]`-целей → сравнить с короткими именами файлов → найти битые ссылки.
3. **Согласованность правил.** Прочитать `AGENTS.md` — проверить отсутствие противоречий, покрытие триггеров.
4. **Auto-memory.** Пройти по `MEMORY.md` и memory-файлам, найти устаревшие или дублирующие vault-страницы записи; сократить до указателей где применимо.
5. **Frontmatter.** Проверить, что у всех страниц есть минимальное ядро (`type`, `tags`, `created`, `updated`).
6. **Untrigger'ed Prevention.** Найти инциденты в incidents-log, у которых секция Prevention не выполнена в виде дополнения других страниц или runbook'а.

**Правила исполнения аудита:**
- Точечные правки делаются сразу в той же сессии (без отдельного ADR).
- Каскадные изменения, обнаруженные в аудите, — отдельный ADR + отдельная сессия.
- Аудит записать в `journal/YYYY-MM-DD.md` как раздел с перечнем найденных проблем и применённых правок.

### 5.7. Параллельные агенты на больших задачах

Паттерн: «один файл — один агент в волне». Применяется для skeleton + waves ([§4.5](#45-структурная-документация-по-паттерну-skeleton--waves)) или массовых каскадных миграций.

**Когда параллелить:**

| Этап | Параллелить? | Причина |
|------|--------------|---------|
| Skeleton-проход | Нет | Hub-страницы и MOC обновляются последовательно, race condition |
| Наполнение волны (component-страницы) | Да | Каждый агент пишет свой набор файлов, нет пересечений |
| Reviewer pass после волны | Нет | Главный агент сверяет результаты |
| Каскадная миграция frontmatter ~50 страниц | Да | Если миграция через скрипт — один агент. Если ручная — 2–3 агента по разделам |

**Правила параллельных агентов:**

1. **Один файл — один агент.** Если двум агентам нужно править один файл — это знак неверного разделения.
2. **Hub-страницы обновляет главный агент.** В waves подсистем — sub-agent пишет только подстраницу, hub обновляет главный после волны.
3. **Reviewer pass — обязательный.** После каждой волны главный агент проверяет Verify-критерии (frontmatter, секции, минимальные связи, актуальный `updated`).
4. **Передача контекста sub-agent'у — три блока:**
   - **Контекст.** Что делается в проекте, в какой фазе сейчас (ссылка на ADR с планом).
   - **Конкретика.** Какие именно файлы создаёт этот sub-agent, по какому шаблону, с какими полями frontmatter.
   - **Жёсткие правила.** Что **нельзя** делать (трогать hub-страницы, выходить за свой набор файлов, создавать ADR).
5. **Sub-agent'ы не запускают sub-agent'ов.** Глубина параллелизма — 1 уровень.

**Типичная волна** (пример):

- Главный агент: подготовил ADR с планом волны (список страниц, разделение по агентам).
- Параллельно запущены 3 sub-agent'а: каждый получает 4–5 страниц для написания.
- После завершения всех sub-agent'ов главный агент делает reviewer pass.
- Главный агент обновляет hub-страницы ссылками на наполненные подстраницы.
- Главный агент обновляет `index.md`, `journal/`, `CHANGELOG.md`.

См. также `docs/workflows.md#parallel-agents`.

## 6. Типичные сценарии

### 6.1. Новый проект — первая сессия после установки

**Дано:** пакет установлен на машину, vault пустой, проект новый или существующий.

**Действия:**

1. Чтение `BOOTSTRAP.md` (даётся пользователем как стартовый промт).
2. Диалог с пользователем: тип проекта, репо, стек, статус, оптика (agent-first / human-first / гибрид).
3. Создание project MOC `wiki/<project>.md` ([§4.2](#42-создание-project-moc)) — минимальная версия.
4. Добавление раздела «Работа над проектом `<project>`» в `AGENTS.md`:
   - Корневая страница проекта — `[[<project>]]`.
   - Где код (если репо есть): относительный путь.
   - Журнал — папка `journal/`.
   - ADR — по обычным правилам, имя `wiki/adr-NNN-...`.
5. Создание `wiki/adr-001-<project>-vault-structure.md` с фиксацией выбора оптики и оси организации.
6. Создание стартовых auto-memory файлов из `auto-memory-templates/`:
   - `user_language.md`.
   - `feedback_technical_autonomy.md`.
   - `feedback_confirm_before_mutations.md`.
   - `project_<project>_context.md`.
   - `MEMORY.md` (индекс).
7. Финальный sweep: `index.md`, `journal/YYYY-MM-DD.md`, `CHANGELOG.md`.

**НЕ делать в первой сессии:**
- Полную структурную документацию всех компонентов (отложено, не одна сессия).
- Создание всех inventory-страниц заранее (создаются по мере проявления).
- Решения про каскадные изменения методологии (отложить).

### 6.2. Существующий проект — onboarding в vault

**Дано:** vault с другим проектом уже существует, добавляется новый.

**Действия:**

1. Прочитать существующий `AGENTS.md` и `methodology-overview.md` — понять текущие правила.
2. Создать MOC нового проекта `wiki/<new-project>.md` независимо от существующего проекта.
3. Добавить новый раздел в `AGENTS.md` (не заменяя существующий проектный раздел): «Работа над проектом `<new-project>`».
4. Auto-memory: добавить `project_<new-project>_context.md`, обновить `MEMORY.md`.
5. Если проекты пересекаются по концептам — двусторонние `[[ссылки]]` между страницами.
6. Если у нового проекта другая оптика — это **не каскад**, оптика выбирается per-project.

### 6.3. Большая структурная документация (skeleton + waves)

**Дано:** проект с >5 компонентами, в vault только верхний уровень. Цель — agent-ready структура.

**Действия (последовательность сессий):**

**Сессия 1 (skeleton):**
1. Разведка кодовой базы: Glob по репо, чтение briefing/docs.
2. Создание ADR `wiki/adr-NNN-<project>-full-structural-documentation.md` с:
   - Context (масштаб системы, текущее состояние vault).
   - Considered options (зеркало / по доменам / гибрид).
   - Pre-flight checks.
   - Decision (обычно гибрид).
   - Migration plan со списком ~N страниц и waves.
3. Создание 5 sub-templates в `wiki/templates/` (если ещё нет).
4. Обновление MOC проекта новой структурой навигации + Mermaid общей архитектуры.
5. Создание N skeleton-страниц по шаблонам с плейсхолдерами `_TBD в волне K_`.
6. Обновление hub-страниц TL;DR + Mermaid + таблица подсистем + ссылки на подстраницы.
7. Обновление `index.md`.
8. Добавление раздела «Reading map» (skeleton) в `<repo>/AGENTS.md`.
9. Запись в `journal/YYYY-MM-DD.md` и `CHANGELOG.md`.

**Сессии 2–5 (waves):**
- Каждая волна — 10–15 страниц по непересекающимся подсистемам.
- Параллельные агенты ([§5.7](#57-параллельные-агенты-на-больших-задачах)).
- Reviewer pass после каждой волны.

**Финализация:**
- Дополнение Reading map по реально проявившимся типовым запросам.
- Обновление auto-memory указателями на ключевые inventory.
- Полный аудит ссылочной целостности.

### 6.4. Инцидент с диагностикой

**Дано:** пользователь сообщает об инциденте.

**Действия:**

1. Открыть `wiki/<project>-incidents-log.md`, добавить раздел по [§2.3](#23-template-incident) со статусом `open`.
2. Заполнить Symptom без интерпретации.
3. Параллельно с диагностикой обновлять разделы: Misdiagnosis (если гипотезы отвергнуты), Root cause (когда найдена).
4. После fix — обновить Fix, поменять Status на `resolved`.
5. **Обязательно Prevention.** Без него инцидент не закрыт.
6. Если Prevention — это новое правило в компоненте: дописать в страницу `<project>-<component>` раздел «Анти-паттерны / gotchas» с обратной ссылкой на инцидент.
7. Если Prevention — это runbook: создать `wiki/runbook-<name>.md`.
8. Если Prevention — это инвариант: дописать в `<project>-invariants`.
9. Auto-memory: указатель в `feedback_*` или `reference_*`, если инцидент повторяющийся.

### 6.5. Передача работы между сессиями (handoff через journal/)

**Дано:** сессия заканчивается, контекст должен пережить «новую сессию через час/день».

**Действия в конце сессии:**

1. `journal/YYYY-MM-DD.md` — обязательно заполнить раздел «Открытые нити»:
   - Что начали и не закончили.
   - Что нужно проверить в следующей сессии.
   - Что пользователь хочет рассмотреть позже.
2. Если есть критичный контекст для сразу-следующей сессии — auto-memory `project_<project>_context.md` обновлён указателем «текущая работа — `[[page-x]]`, открытые вопросы — `journal/YYYY-MM-DD#открытые-нити`».
3. `CHANGELOG.md` — короткая запись.

**Действия в начале новой сессии:**

1. Auto-memory подгружается автоматически.
2. Если запуск из vault — читать последние 1–2 записи `journal/`.
3. Если запуск из репо кода — читать `<repo>/AGENTS.md` (Reading map), затем релевантные страницы vault.
4. Перед первым содержательным действием — кратко в ответе сверить с пользователем, на чём остановились (одна-две строки).

## 7. Anti-patterns и gotchas

Зафиксированные ошибки, замеченные в реальных кейсах применения методологии. Избегай их.

### 7.1. Дублирование между vault и кодом

**Антипаттерн:** в vault страница описывает имена функций, структуру классов, поля API в полной точности.

**Почему плохо:** vault устаревает при следующем рефакторинге кода. Vault теряет авторитет как источник истины.

**Правило:** в vault — мотивация, инварианты, контекст решения, ссылки на код относительными путями. Не дублируй имена и структуру. Если факт можно получить из кода — оставь только ссылку.

**Пример (правильно):**
```markdown
## Реализация

| Подмодуль | Файл | Что делает |
|-----------|------|------------|
| Channel manager | `../<repo>/core/channels.py` | Lifecycle торговых каналов |
```

**Пример (неправильно):**
```markdown
## Реализация

`ChannelManager.create()` принимает параметры `symbol`, `direction`, `lot`, `grid_step`. Возвращает `Channel`.
```

Это устареет при первом переименовании метода.

### 7.2. Преждевременное создание файлов

**Антипаттерн:** агент пишет файлы до согласования общей картины с пользователем.

**Почему плохо:** часть файлов оказывается ненужной / неправильно структурированной / с конфликтующими именами.

**Правило:** для нетривиальных задач (>5 файлов, новые структурные решения) — план в чате с пользователем, потом файлы. Для тривиальных триггеров (обработай raw, зафиксируй решение) — сразу действие.

**Граница:** если число затрагиваемых файлов > 5 ИЛИ операция меняет структуру методологии — план обязательно.

### 7.3. Битые wikilinks при параллельной работе агентов

**Антипаттерн:** два sub-agent'а в волне создают ссылки друг на друга, но один из них не создаёт обещанную страницу.

**Почему плохо:** битые `[[ссылки]]` в наполненных страницах после волны.

**Правило:** в задании каждому sub-agent'у явно прописан список страниц, которые он создаёт. Sub-agent ссылается только на:
- Свои страницы (которые точно создаёт).
- Страницы, которые точно существуют до волны (skeleton + hub'ы + MOC).
- Страницы из задания другого sub-agent'а в этой волне (только если задание явно перечисляет их имена).

Reviewer pass проверяет битые ссылки Grep'ом.

### 7.4. Hub-страницы как race-condition area

**Антипаттерн:** sub-agent при создании подстраницы пытается обновить hub-страницу, ссылающуюся на него.

**Почему плохо:** если 3 sub-agent'а пытаются обновить один hub — последний перезаписывает первых.

**Правило:** sub-agent **не трогает hub-страницы**. Hub обновляет главный агент в reviewer pass.

В задании sub-agent'у явно: «Не редактируй файлы: `<project>.md`, `<project>-<hub-1>.md`, ..., `index.md`, `journal/`, `CHANGELOG.md`».

### 7.5. Замена narrative на декларативность

**Антипаттерн:** агент пишет страницы narrative-стилем («Эта подсистема была создана, потому что... затем мы решили, что... но в итоге пришли к выводу...»).

**Почему плохо:** агенты-читатели тратят больше токенов на разбор. Не работают inventory и Dataview-запросы (нет таблиц с фиксированной структурой).

**Правило для agent-first:** declarative-стиль. TL;DR → bullets → таблицы → Mermaid. Narrative только в секции «Идея» (1–2 абзаца) и «Источник».

**Исключение:** ADR пишутся в narrative-стиле в разделах Context, Decision, Consequences — это намеренно, ADR читается людьми тоже.

### 7.6. Двойной пересмотр оптики

**Антипаттерн:** через 2 сессии после bootstrap пользователь говорит «давай поменяем оптику» (с agent-first на human-first или наоборот).

**Почему плохо:** все созданные страницы либо переписываются (большой каскад), либо vault становится несогласованным.

**Правило:** оптика фиксируется в ADR-001 проекта в первой сессии. Если возникает желание поменять — это явный каскадный ADR с Migration plan. Не делать «по чуть-чуть» в обычных сессиях.

### 7.7. Auto-memory как копия vault

**Антипаттерн:** в auto-memory сохраняется полный текст знания (концепты, факты, история).

**Почему плохо:** auto-memory разрастается, дублирует vault, выходит из синхронизации.

**Правило:** auto-memory — только указатели типа «по теме X — `[[page-x]]`», «эталон для запроса Y — `[[inventory-z]]`», «правило: при triggering X сначала сделать Y». Содержание знаний — в vault.

### 7.8. Игнорирование секции Prevention в инцидентах

**Антипаттерн:** инцидент закрыт со статусом `resolved`, но секция Prevention пустая или содержит только «исправили баг».

**Почему плохо:** инцидент повторяется через несколько недель. Урок потерян.

**Правило:** статус `resolved` ставится только когда Prevention выполнена в виде:
- Дополнения страницы компонента (раздел «Анти-паттерны»).
- Нового или обновлённого runbook'а.
- Нового инварианта в `<project>-invariants`.
- Изменения в `AGENTS.md` (правило поведения агента).

Если ничего из перечисленного не подошло — Prevention описывает явное наблюдение «впредь делать X».

### 7.9. Глубокая иерархия в названиях страниц

**Антипаттерн:** имена файлов с 4+ уровней (например `<project>-server-routes-admin-v1-license-create.md`).

**Почему плохо:** ссылки `[[...]]` становятся длинными и хрупкими. Reorg ломает много страниц.

**Правило:** максимум 3 уровня в kebab-case: `<project>-<component>-<aspect>`. Дальнейшая детализация — внутри страницы как разделы, не как новые файлы.

### 7.10. Frontmatter без значимости

**Антипаттерн:** все страницы имеют `type: concept`, все теги `[methodology]`, все `layer: kernel`.

**Почему плохо:** Dataview-запросы перестают разделять. Frontmatter становится мёртвым полем.

**Правило:** ставить честные значения. Если страница не вписывается в существующие — это знак расширить enum в ADR, а не «выбрать ближайшее».
