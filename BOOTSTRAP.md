# BOOTSTRAP — первая сессия Claude в claude-knowledge-base

## Для кого этот документ

Привет, Claude. Ты в шаблонной папке `claude-knowledge-base`. Эта папка — переносимый пакет методологии «второй мозг»: пустой Obsidian-vault, конституция, шаблоны страниц, заготовки auto-memory и playbook для тебя.

Сейчас твоя единственная задача — **выполнить bootstrap**: настроить методологию под этого пользователя и его проект, прежде чем переходить к содержательной работе. Этот документ — исполняемый промт, не описание процесса. Каждый раздел ниже — действие, которое ты выполняешь.

Действуй во втором лице к себе: «я читаю», «я задаю вопрос», «я создаю файл». Не пересказывай пользователю что ты собираешься делать — делай, и в конце выдай финальный отчёт.

**Жёсткое правило bootstrap:** до завершения всех 8 шагов в разделе «Действия после ответов» — не запускать никакую содержательную работу (не обрабатывать `raw/`, не создавать страницы wiki под темы пользователя, не отвечать на вопросы о его проекте). Bootstrap — отдельная сессия с одной целью.

**Исключение из правила** (см. раздел «Что если пользователь хочет содержательную работу до завершения bootstrap» ниже) — пользователь явно просит отложить bootstrap или ответить на конкретный вопрос. В этом случае действуй прагматично.

## Что прочитать перед началом

В этом порядке (важен порядок, не пропускать):

1. **`AGENT-MANUAL.md`** в корне пакета — главный playbook. Объясняет как ты работаешь с этой методологией в любой сессии (не только bootstrap): 3 слоя памяти, ADR/runbook/incident workflow, agent-first шаблоны, paths-структура, типы страниц wiki, как кастомизировать vault под крупный проект.
2. **`obsidian-aura/AGENTS.md`** — конституция vault'а. Это процедурный слой памяти. После bootstrap ты будешь читать его при каждом запуске в папке vault.
3. **`obsidian-aura/wiki/methodology-overview.md`** — общая карта методологии: что где живёт, как связаны 3 слоя памяти, какие типы страниц существуют, когда применять каждый шаблон.
4. **Этот файл (`BOOTSTRAP.md`)** — ты уже здесь. Перечитай раздел «Действия после ответов» — это твой чек-лист на оставшуюся часть сессии.
5. **`docs/customization.md`** — extended-документ про кастомизацию vault под крупный проект. Понадобится, если пользователь укажет проект с большой архитектурой (см. шаг 1 ниже).

После чтения этих 5 артефактов у тебя должна сложиться полная картина: что такое vault, какие у него слои памяти, какие триггеры пользователя имеют автоматическую реакцию, какие типы страниц существуют и как они связываются.

Не читай больше ничего до завершения вопросов — лишняя информация на этой стадии не нужна.

## Pre-flight: проверка на повторный запуск

**До задавания любых вопросов** проверь, не был ли bootstrap запущен раньше. Это убережёт от перезаписи проделанной работы.

Сделай 3 быстрые проверки:

1. **Glob `obsidian-aura/wiki/*.md`** — есть ли там MOC проекта (не `methodology-overview.md`, не `templates/*`)?
2. **Grep по `obsidian-aura/AGENTS.md`** на строку «## Работа над проектом» — есть ли раздел?
3. **Read** auto-memory MEMORY.md (см. шаг 3 ниже про путь) — заполнен ли?

**Если ничего из этого не нашлось** — bootstrap чистый, продолжай к разделу «Вопросы пользователю».

**Если что-то нашлось частично** (например, MOC есть, но AGENTS.md без раздела) — bootstrap был прерван. Переходи в раздел «Recovery (если bootstrap прервался)» в конце этого файла.

**Если все три проверки прошли** (MOC есть, AGENTS.md содержит раздел, auto-memory заполнено) — bootstrap уже выполнялся ранее полностью. Спроси пользователя:

> «Bootstrap уже выполнен. Хочешь пересоздать? Введи "пересоздать" чтобы продолжить (это перезапишет project MOC и AGENTS.md разделы), или "выйти" чтобы перейти к содержательной работе.»

При ответе «выйти» — bootstrap завершён, жди следующего сообщения. При «пересоздать» — продолжай с раздела «Вопросы пользователю», но каждый шаг ниже подчиняется idempotency-правилам (перезапись только после подтверждения).

## Вопросы пользователю (4 шт.)

### Q1: Проект и окружение (свободный текстовый вопрос)

Q1 — **обычный текстовый вопрос Claude к пользователю**, не AskUserQuestion. Задай его до AskUserQuestion-блока с Q2-Q4, отдельным сообщением (или в начале сообщения, в котором следом идёт AskUserQuestion).

**Точная формулировка для пользователя:**

> «Есть ли проект, под который настраиваем vault? Назови:
> - имя проекта,
> - локальный путь к коду (если есть),
> - ссылку на GitHub-репо (если есть),
> - операционную систему (Windows / macOS / Linux).
>
> Если проекта нет — отвечай "без проекта".»

**Из ответа извлеки переменные:**

| Переменная | Источник в ответе | Если отсутствует |
|------------|-------------------|------------------|
| `<project-name>` | Имя проекта | Если «без проекта» / «нет проекта» / «не сейчас» — пометить `<project-name> = none`, project-зависимые шаги (1, 2, project_*_context.md в шаге 3) пропустить. |
| `<project-path>` | Локальный путь | Опционально. Если нет — оставить поле пустым в project MOC и AGENTS.md разделе. |
| `<github-url>` | GitHub URL | Опционально. Аналогично. |
| `<os>` | ОС | **Обязательно.** Если в ответе нет упоминания ОС — задай follow-up: «На какой ОС работаешь — Windows, macOS или Linux? Это нужно для команд symlink и путей auto-memory.» |

**Правила интерпретации:**

- «без проекта» / «нет проекта» / «не сейчас» / «нет» / «no project» → `<project-name> = none`. Не задавай follow-up про путь/GitHub в этом случае — они нерелевантны.
- Если пользователь дал имя проекта, но не указал ни путь, ни GitHub, ни ОС — задай **один** follow-up, в котором сразу спроси все недостающие поля. Не пингуй по одному.
- Если пользователь дал имя проекта и ОС, но без пути/GitHub — это нормально, не задавай follow-up. Поля опциональные.
- Если ответ совсем неинформативен («да», «есть проект») — переспроси с уточнением: «Уточни — как называется проект, где код, какая ОС?»

После того как все нужные переменные извлечены — переходи к AskUserQuestion-блоку с Q2-Q4.

### Q2-Q4: язык, уровень, автономность (один AskUserQuestion-блок)

Задай эти 3 вопроса **одним блоком `AskUserQuestion`** (3 questions в одном вызове). Без предисловий — пользователь уже ответил на Q1 и знает, что идёт bootstrap.

#### Q2: Язык общения

**Question:** «На каком языке тебе общаться со мной (тексты ответов, объяснения, планы)? Код, имена файлов, технические термины (commit, branch, lint) остаются на английском в любом случае.»

**Header:** «Язык»

**multiSelect:** false

**Options:**
- `Русский` — все тексты на русском, техтермины на английском.
- `English` — all responses in English.
- `Mixed` — отвечать на языке последнего сообщения пользователя.

#### Q3: Технический уровень пользователя

**Question:** «Какой у тебя технический уровень? Это влияет на то, как я объясняю и какие вопросы тебе задаю.»

**Header:** «Уровень»

**multiSelect:** false

**Options:**
- `Программист` — могу обсуждать архитектуру, выбор библиотек, паттерны.
- `Не программист` — даю цели на естественном языке, не разбираюсь в main/branch/PR/granularity, технические решения принимай сам.
- `Частично` — разбираюсь в общих понятиях, но детали реализации оставляю тебе.

#### Q4: Автономность

**Question:** «Как мне действовать со стандартными mutation-операциями (commit, push, создание файлов, правки в vault)?»

**Header:** «Автономность»

**multiSelect:** false

**Options:**
- `Автономно` — действуй сам по стандартам методологии, без подтверждений. Спрашивай только при выходе за scope задачи.
- `С подтверждением` — перед любой mutation-операцией спрашивай разрешения отдельно.
- `Гибрид` — стандартные операции в рамках задачи (commit/push в текущей ветке, обновление существующих страниц) — без подтверждения; необратимые или вне scope (force-push, удаление файлов, изменение прод-инфры) — с подтверждением.

---

После получения ответов на Q1 (текст) и Q2-Q4 (AskUserQuestion) **не комментируй** их вслух — переходи сразу к действиям. Все 4 ответа влияют на следующие шаги.

## Действия после ответов (8 шагов)

Выполняй последовательно. Каждый шаг — независимая единица; если шаг неприменим (например, пользователь сказал «без проекта» — пропусти project MOC), явно отметь это в финальном отчёте.

**Idempotency — общий принцип:** перед каждой мутацией проверь текущее состояние артефакта. Если артефакт уже существует — действуй по правилу, прописанному в шаге (skip / спросить / append). Никогда не перезаписывай без явной проверки или согласия пользователя.

### Шаг 1 — Project MOC (если проект задан)

Если в Q1 пользователь назвал проект (т.е. `<project-name> ≠ none`):

**Idempotency-проверка (первое действие шага):** Read `obsidian-aura/wiki/<project-slug>.md`.

- Если файл существует — спроси пользователя: «MOC проекта `<project-slug>` уже существует. Перезаписать? (Y/n) Дефолт: нет.» При ответе «нет» / пустом ответе / «n» — пропусти создание, отметь в финальном отчёте «MOC проекта уже существовал, сохранён без изменений». При «Y» / «да» — переходи к созданию (перезапись).
- Если файла нет — переходи к созданию.

**Создание:**

`<project-slug>` — kebab-case имени проекта (только латиница и дефисы, без пробелов и кириллицы, без расширения проекта типа `.com`).

Структура страницы (используй шаблон `template-component.md` как образец для структурных секций, но это **MOC**, не component):

```markdown
---
type: moc
tags: [<project-slug>, methodology]
created: <YYYY-MM-DD>
updated: <YYYY-MM-DD>
---

# <Имя проекта>

Короткое summary в 1-2 строки: что это за проект, какая у него цель.

## Точка входа

Это MOC (Map of Content) проекта. Все страницы про <проект> добавляются сюда.

## Архитектура

_Заполняется по мере появления знаний о проекте. Сейчас известно:_
- Локальный путь к коду: `<путь из Q1, если есть>`
- GitHub: `<url из Q1, если есть>`
- ОС: `<из Q1>`

## ADR

_Архитектурные решения — `wiki/adr-NNN-<тема>.md`, ссылки добавляются здесь._

## Runbook'и

_Операционные процедуры — `wiki/runbook-<тема>.md`, ссылки добавляются здесь._

## Inventory / Domain hubs (если применимо)

_Появляются при росте проекта (>5 компонентов) — см. `docs/customization.md` раздел «agent-first структурная документация»._

## Журнал

Последние записи — в `obsidian-aura/journal/`, помечены тегом `<project-slug>` в frontmatter.

## Связано с

- [[methodology-overview]] — как устроена база знаний
- [[AGENTS]] — конституция

## Источник

Bootstrap-сессия <YYYY-MM-DD>, ответы пользователя на Q1.
```

Если проект не назван — этот шаг пропускается, переходи к шагу 2.

### Шаг 2 — Раздел «Работа над проектом X» в AGENTS.md

Если проект задан:

**Idempotency-проверка (первое действие шага):** Read `obsidian-aura/AGENTS.md`, Grep на строку `## Работа над проектом` (без привязки к имени) внутри этого файла.

- Если раздел уже есть и содержит имя текущего проекта — skip, отметь в финальном отчёте «раздел в AGENTS.md уже присутствует».
- Если раздел есть, но для **другого** проекта — спроси: «В AGENTS.md уже есть раздел про другой проект (`<old-name>`). Заменить на `<new-name>`? (Y/n) Дефолт: нет.» При «нет» — skip с warning «vault настроен под другой проект, требуется ручная переконфигурация». При «Y» — заменить.
- Если раздела нет — добавь его (после раздела «Память Claude», до раздела «Шаблоны страниц»).

**Контент раздела:**

```markdown
## Работа над проектом <Имя проекта>

Этот vault — операционная среда работы над проектом <Имя проекта> (<краткое описание из Q1, если есть путь к коду — упомянуть его>). Принципы такой работы:

**Разделение источников истины.** Код в `<путь>` — единственный источник истины о том, как проект работает прямо сейчас. Vault — единственный источник истины о том, что мы решили, почему мы это решили, и какой контекст за этим стоял.

**Корневая страница проекта.** Точка входа — [[<project-slug>]] в `wiki/`. Любая новая страница про проект добавляется в эту разводку.

**Журнал работы.** Папка `journal/` содержит дневник работы. Каждая значимая сессия фиксируется заметкой `YYYY-MM-DD.md` или `YYYY-MM-DD-<тема>.md`.

**Архитектурные решения (ADR).** Нетривиальные технические решения — `wiki/adr-NNN-<тема>.md` по шаблону `template-adr.md`.

**Связь страниц wiki с кодом.** Страницы, описывающие конкретные части кода, ссылаются на файлы относительным путём (`../<repo>/path/to/file`). При значительных рефакторингах эти ссылки обновляются.

**Когда проект вырастет до >5 компонентов с нетривиальной архитектурой** — применить agent-first структурный паттерн (skeleton + waves + параллельные агенты, 5 типов страниц). Подробности — `docs/customization.md`.
```

Это раздел AGENTS.md, не отдельная страница. Шаблон `template-component.md` — образец **стиля** для разделов, не source файла.

Если проект не задан — этот шаг пропускается.

### Шаг 3 — Auto-memory из шаблонов

Auto-memory — эпизодический слой памяти. Файлы кладутся в платформо-зависимую папку:

- **Windows:** `%USERPROFILE%\.claude\projects\<encoded-install-path>\memory\`
  где `<encoded-install-path>` — install-путь, в котором каждый разделитель пути (`:`, `\`, `/`) заменён на `-`. Пример: для install `C:\Users\Alice\dev\my-vault` → `c--Users-Alice-dev-my-vault`.
- **macOS:** `~/.claude/projects/<encoded-install-path>/memory/`
- **Linux:** `~/.claude/projects/<encoded-install-path>/memory/`

**Idempotency-проверка (первое действие шага):**

1. Test-Path / Glob папку `<memory-dir>/`. Если не существует — создай.
2. Если уверенности про install-path нет — спроси install-path отдельным сообщением (это уточнение по факту, не AskUserQuestion).
3. Для каждого ниже-перечисленного файла, который ты собираешься скопировать, **сначала Read** в `<memory-dir>/`. Если файл уже есть — **skip копирование**, выдай warning «`<filename>` уже существует в auto-memory, оставлен без изменений». **Не перезаписывай.**
4. Особый случай: `MEMORY.md` уже существует. Не перезаписывай. Если в нём нет ссылки на какой-то из скопированных в этой сессии файлов — добавь ссылку отдельной строкой, не трогая остальное содержимое.

**Из шаблонов в `auto-memory-templates/`** скопируй и активируй (убрать суффикс `.example` из имени) **только нужные** файлы — по ответам пользователя:

| Файл шаблона | Когда копировать | Что заполнить |
|--------------|------------------|---------------|
| `MEMORY.md.example` | **Всегда** (если ещё нет в memory-dir) | Индекс auto-memory — список других memory-файлов с короткими описаниями. |
| `user_language.md.example` | Если Q2 ≠ English | Подставить язык из Q2 в body. |
| `user_role.md.example` | Если Q3 ≠ «Программист» | Подставить роль из Q3, добавить пометки про тон/глубину технических объяснений. |
| `feedback_technical_autonomy.md.example` | Если Q4 = «Автономно» | Без изменений тела (шаблон уже описывает автономность). Подставить дату в frontmatter. |
| `feedback_confirm_before_mutations.md.example` | Если Q4 = «С подтверждением» или «Гибрид» | Подставить вариант из Q4. |
| `project_<slug>_context.md` | Если проект задан (Q1 ≠ none) | Создать **новый файл** (не из шаблона — этот тип в auto-memory-templates не лежит, потому что слишком project-specific). Минимальное содержимое: указатель на [[<project-slug>]] MOC в vault + локальный путь к коду + GitHub-url. Frontmatter `type: project`. |

Для каждого скопированного файла:
1. Обнови frontmatter: `created: 2026-05-21`, `updated: 2026-05-21` (или текущую дату сессии, если расхождение).
2. Заполни placeholder'ы из body содержательно — не оставлять `<язык>`, `<роль>` и т.п. как литералы.

**MEMORY.md** наполни ссылками только на реально скопированные файлы. Не добавляй ссылки на проекты, тегов которых нет (например, если пользователь сказал «без проекта» — нет строки «project context»).

### Шаг 4 — Symlink AGENTS.md в корне install-папки

Цель: чтобы при запуске Claude в корне install-папки (например, в `<install-dir>/`) автоматически загружалась конституция vault. Без symlink'а Claude Code подгружает AGENTS.md только из cwd и родителей — не из подпапок.

**Idempotency-проверка (первое действие шага):**

1. Test-Path `<install-dir>/AGENTS.md`.
2. Если файл существует — проверь, является ли он symlink'ом на правильное место (`<install-dir>/obsidian-aura/AGENTS.md`).
   - Если да — skip, отметь в финальном отчёте «symlink AGENTS.md уже создан».
   - Если файл существует и **не** symlink (или ссылается куда-то ещё) — выдай warning: «`<install-dir>/AGENTS.md` уже существует и не является symlink на `obsidian-aura/AGENTS.md`. Возможно, остался от прошлой установки. Пользователь должен удалить вручную перед созданием symlink'а.» Команду на удаление и создание включи в финальный отчёт.
3. Если файла нет — переходи к подсказке команды.

Подскажи пользователю команду для его ОС (из Q1). **Не запускай команду сам** — она требует Administrator (Windows) или sudo (Linux). Дай пользователю команду как текст:

**Windows (PowerShell под Administrator):**
```
mklink "<install-dir>\AGENTS.md" "<install-dir>\obsidian-aura\AGENTS.md"
```

**macOS/Linux (терминал из install-dir):**
```
ln -s "obsidian-aura/AGENTS.md" "AGENTS.md"
```

Если у пользователя нет прав Administrator — альтернатива (Windows): обычная копия файла + ручная синхронизация, либо junction для папки (`mklink /J`). Это hack, не рекомендуется — лучше получить права один раз.

Подсказку дай в финальном отчёте (шаг 8), не блокируй bootstrap на это действие.

### Шаг 5 — CHANGELOG.md

CHANGELOG — **append-only**. Никогда не перезаписывай существующие записи.

**Idempotency-проверка (первое действие шага):** Read `obsidian-aura/CHANGELOG.md`. Грепни по сегодняшней дате (`## 2026-05-21`).

- Если записи от сегодняшней даты **нет** — добавь новую запись в начало файла:
  ```markdown
  ## 2026-05-21

  - **Установка пакета claude-knowledge-base v<VERSION>** (см. `VERSION` в корне install).
  - Bootstrap-сессия: ответы пользователя зафиксированы в auto-memory + project MOC создан (если применимо).
  - Symlink AGENTS.md — подсказан пользователю, требует ручного выполнения с правами admin/sudo.
  ```
- Если запись от сегодняшней даты **уже есть** (например, был частичный bootstrap раньше сегодня) — не сливай в существующую секцию. Добавь **sub-раздел с timestamp** внутри той же даты:
  ```markdown
  ## 2026-05-21

  ### <HH:MM> bootstrap continuation
  - Bootstrap resumed (см. журнал `journal/2026-05-21-install-*.md`).
  - <конкретные действия этой итерации>

  <предыдущий контент даты сохраняется ниже>
  ```

Если CHANGELOG ещё не существует (пустая заготовка vault без файла) — создай со сегодняшней записью + минимальным заголовком файла.

### Шаг 6 — Журнал bootstrap-сессии

Журнал — **append-only** (одна заметка на сессию).

**Idempotency-проверка (первое действие шага):** Glob `obsidian-aura/journal/2026-05-21-install*.md`.

- Если файлов с таким префиксом нет — создай `obsidian-aura/journal/2026-05-21-install.md`.
- Если файл `2026-05-21-install.md` уже существует — это был прерванный bootstrap. Создай **новый файл** с timestamp: `obsidian-aura/journal/2026-05-21-install-resumed-<HH-MM>.md`. В нём упомяни в первой строке «продолжение от <предыдущий-файл>».
- Не перезаписывай существующий journal-файл.

**Контент журнала:**

```markdown
---
type: journal
tags: [bootstrap, methodology, install]
created: 2026-05-21
updated: 2026-05-21
---

- Дополнен `obsidian-aura/AGENTS.md` разделом про проект (или «не применимо» / «уже присутствовал»).
```

### Шаг 7 — Dataview-плагин

Read-only шаг, idempotency не нужен.

Dataview нужен для динамических индексов в `methodology-overview.md` и project MOC. Если ты не можешь проверить, установлен ли он (Obsidian — внешнее приложение), просто подскажи пользователю:

«Если Obsidian запущен — открой Settings → Community plugins → Browse → найди "Dataview" → Install → Enable. Это даст работающие динамические запросы в `methodology-overview.md` и MOC проекта. Без Dataview vault работает, но запросы в шаблонах отображаются как блоки кода вместо таблиц.»

Эту подсказку включи в финальный отчёт (шаг 8). Сам ничего не устанавливай — у тебя нет доступа к плагинам Obsidian.

### Шаг 8 — Финальный отчёт пользователю

Read-only шаг (генерация текстового отчёта), idempotency не нужен.

Только после всех 7 предыдущих шагов выдай отчёт. Структура отчёта:

```markdown

- Раздел «Работа над проектом» в `obsidian-aura/AGENTS.md` — если применимо. Аналогично с пометками.
   ```

## Recovery (если bootstrap прервался)

Если в pre-flight-проверке (см. начало этого файла) ты обнаружил **частичное состояние** — какие-то артефакты bootstrap есть, какие-то нет — bootstrap был прерван (например, упала сессия, или пользователь закрыл чат на середине). Не запускай заново все 8 шагов с нуля.

### Алгоритм recovery

1. **Прочитай состояние** (read-only inventory):
   - Glob `obsidian-aura/wiki/*.md` — какие MOC проектов уже есть.
   - Grep `obsidian-aura/AGENTS.md` на «## Работа над проектом» — есть ли раздел и для какого проекта.
   - Read auto-memory `MEMORY.md` и Glob соседние файлы — какие memory-файлы уже скопированы.
   - Test-Path `<install-dir>/AGENTS.md` — есть ли symlink.
   - Read `obsidian-aura/CHANGELOG.md` — есть ли запись от сегодняшней даты.
   - Glob `obsidian-aura/journal/2026-05-21-install*.md` — есть ли journal-файл сессии.

2. **Определи на каком шаге остановилось.** Соответствие артефактов и шагов:

   | Артефакт | Шаг |
   |----------|-----|
   | `wiki/<project>.md` (MOC проекта) | Шаг 1 |
   | Раздел в AGENTS.md | Шаг 2 |
   | Файлы в auto-memory `memory/` | Шаг 3 |
   | Symlink `<install-dir>/AGENTS.md` (или подсказка в журнале) | Шаг 4 |
   | Запись в CHANGELOG за сегодня | Шаг 5 |
   | Файл `journal/2026-05-21-install*.md` | Шаг 6 |

   Самый ранний шаг, артефакт которого отсутствует — точка возобновления.

3. **Восстанови недостающий input от пользователя.** Не задавай Q1-Q4 заново целиком — используй существующее состояние:
   - Имя проекта — из project MOC (если есть) или из раздела AGENTS.md.
   - Язык, уровень, автономность — из auto-memory файлов (`user_language.md`, `user_role.md`, `feedback_*`).
   - Локальный путь / GitHub / ОС — из секции «Архитектура» project MOC или из `project_*_context.md` в auto-memory.

   Если какое-то поле отсутствует (например, язык установлен, но автономность нет) — задай **только недостающий** вопрос. Не пингуй по уже известным полям.

   Если состояние совсем непонятно (артефакты есть, но противоречат друг другу) — спроси пользователя: «Нашёл следы предыдущего bootstrap. Перечислю что вижу: <список>. Хочешь продолжить с того места или начать заново?»

4. **Продолжи с найденного шага.** Каждый последующий шаг выполняй идемпотентно по правилам секции «Действия после ответов» — проверки в начале каждого шага уже описаны.

5. **Финальный отчёт.** В финальном отчёте (шаг 8) упомяни «bootstrap resumed from step <N>» (где `<N>` — номер шага, с которого продолжили). Это сигнал пользователю что часть работы была сделана в прошлой сессии.

### Recovery vs полный повтор

| Состояние | Действие |
|-----------|----------|
| Ничего не нашлось в pre-flight | Полный bootstrap с Q1. |
| Частичное состояние (какие-то артефакты есть) | Recovery по алгоритму выше. |
| Все 6 ключевых артефактов есть, и пользователь повторно запустил bootstrap | Спросить «пересоздать или выйти», см. pre-flight. |

## Что если пользователь хочет содержательную работу до завершения bootstrap

Жёсткое правило «не отвечать на содержательное» — стандарт. Но бывают разумные исключения.

Если пользователь явно говорит «забудь bootstrap», «ответь на X сейчас», «не настраивай ничего», «потом настроим» — действуй прагматично:

- **Если содержательная работа НЕ требует project-контекста** (общий вопрос про Claude Code, методологию, общую тему программирования, мета-вопрос про сам пакет) — отвечай прямо. После ответа спроси: «Возобновить bootstrap?» Если пользователь скажет «нет» — оставь как есть, в следующей сессии pre-flight подскажет, что bootstrap не завершён.
- **Если содержательная работа требует project-контекста, которого нет** (например, «расследуй баг в моём проекте X» а MOC ещё не создан, путь к коду не указан) — попроси сначала завершить минимум Q1 («просто скажи имя проекта и где код, дальше bootstrap можно отложить»). Без этого ответ будет основан на догадках и нанесёт больше шума, чем пользы.
- **Если содержательная работа требует project-контекста, и он частично есть** (например, project MOC создан, но AGENTS.md ещё не обновлён) — ответь, используя что есть. После ответа спроси: «Возобновить bootstrap с оставшихся шагов?»

Не пытайся сам решить за пользователя. Если он сказал «забудь bootstrap» — значит у него причина. Твоя задача — не блокировать его работу формальностями, но и не игнорировать риск выдуманных ответов из-за нехватки контекста.

## Финальный отчёт пользователю

См. шаг 8 — это и есть финальный отчёт. После него — жди следующего сообщения пользователя. Не начинай обрабатывать `raw/`, не задавай ничего, не предлагай дополнительных действий. Ты в режиме ожидания первой содержательной задачи.

## Anti-patterns

Чего **не делать** в bootstrap-сессии:

- **Не запускать содержательную работу** до завершения шага 8 — **за исключением** случаев, описанных в разделе «Что если пользователь хочет содержательную работу до завершения bootstrap».
- **Не пропускать вопросы из соображений «и так понятно».** 4 вопроса — единственный legitimate-источник project-specific фактов. Без них любые auto-memory будут выдуманы.
- **Не создавать auto-memory без ответов пользователя.** `feedback_technical_autonomy.md.example` копируется ТОЛЬКО если Q4 = «Автономно». Не превентивно «на всякий случай».
- **Не выдумывать project-specific факты.** Если пользователь не сказал, какой у проекта стек, какие компоненты, какая архитектура — НЕ домысливать. Project MOC создаётся скелетом, наполнение появится в дальнейших сессиях.
- **Не пропускать Q1 ради скорости.** Даже если пользователь сказал «без проекта» — Q2-Q4 всё равно задать. Слой `user`/`feedback` относится к пользователю, не к проекту.
- **Не оформлять Q1 как AskUserQuestion** с фиктивной опцией «Ввести вручную». Q1 — обычный текстовый вопрос (см. секцию «Q1: Проект и окружение»).
- **Не использовать AskUserQuestion с техническими опциями типа «выбрать репо», «слой памяти», «структуру MOC».** Q2-Q4 в этом BOOTSTRAP — про цели и предпочтения пользователя, не про реализацию. Если в процессе возникнет техническая развилка — выбирай по best-practice сам (особенно если Q3 ≠ «Программист»).
- **Не редактировать AGENTS.md содержательно** (правила, конституция). Только добавить раздел «Работа над проектом X». Конституция — общая, project-агностичная.
- **Не создавать symlink самостоятельно** через mklink/ln — это требует прав, которых у тебя нет. Подсказать команду пользователю.
- **Не перезаписывать существующие артефакты без проверки.** Idempotency-проверка — первое действие каждого шага. См. правила в каждом шаге.

## Troubleshooting (краткий)

| Проблема | Действие |
|----------|----------|
| Не могу определить install-path для auto-memory | Спросить пользователя одним вопросом вне AskUserQuestion. |
| Путь к `~/.claude/projects/.../memory/` уже содержит файлы | Не перезаписывать. Слить с шаблонными (placeholder'ы из шаблонов добавить как новые секции в существующий MEMORY.md). См. шаг 3, idempotency-проверка. |
| Пользователь сказал «без проекта», но потом в Q4 выбрал «Автономно» | Скопировать `feedback_technical_autonomy.md.example` — это user-level feedback, не project-specific. Project MOC не создаётся. |
| Obsidian не запущен у пользователя | Bootstrap не зависит от запуска Obsidian. Шаг 7 (Dataview) — просто подсказка на потом. |
| Symlink mklink выдаёт ошибку «privileges not held» | Подсказать пользователю запустить PowerShell под Administrator. Альтернатива (worse): использовать `mklink /J` для junction-папки, но это меняет семантику (junction на папку, не файл) — лучше получить admin-права. |
| Pre-flight нашёл частичные артефакты | Перейти в раздел «Recovery (если bootstrap прервался)». |
| Pre-flight нашёл все артефакты, пользователь запросил повторный bootstrap | Спросить «пересоздать или выйти» (см. pre-flight). |
| Пользователь в Q1 не указал ОС | Follow-up: «На какой ОС работаешь — Windows, macOS или Linux?» Это нужно для symlink-команды и пути auto-memory. |
| Пользователь в Q1 дал только имя проекта без пути/GitHub/ОС | Один follow-up со всеми недостающими полями (не пинговать по одному). |

Полный troubleshooting — `docs/troubleshooting.md` (если присутствует в пакете).
