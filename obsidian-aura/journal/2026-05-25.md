# 2026-05-25 (вторая сессия) — MSI uninstall с опциональной очисткой данных

## Контекст

Пользователь поручил: «Необходимо обновить проект так, чтобы при деинсталляции ПО можно было бы установить галочку и удалить все файлы проекта с устройства».

PHASE 1 открыл: [[auragrid]] MOC, [[runbook-vault-integration]], journal `2026-05-24.md` и `2026-05-25.md` (первая сессия), auto-memory `feedback_release_checklist` (старая боль — после нового MSI данные в `%APPDATA%\GridScalp\` не перезаписываются) и `project_python_embed_packaging`. Контекст: AuraGrid собирается в MSI через Tauri v2 + WiX 3 (`bundle.targets: ["msi"]`, `UpgradeCode: 2B9B9F5C-1A71-4C4F-9D7E-6A9F0F5B6C11`), Tauri использует `WixUI_InstallDir`. Папка пользовательских данных — `%APPDATA%\GridScalp\` (lib.rs::appdata_root, appdata.rs::root, bot_process.rs::appdata_dir, crash_report.rs::appdata_dir, analytics.rs::appdata_dir — все собирают тот же путь). Уже существует Tauri-команда `reconfigure_wizard` — частично чистит файлы, но НЕ удаляет папку целиком (соответствует `feedback_release_checklist`).

## Дизайн-выбор (анти-вариант рассмотрен)

**Альтернатива «галочка в WiX UI»** — отвергнута. Стандартный uninstall через «Программы и компоненты» Windows запускается с basic UI (только progress bar) — никаких maintenance dialog не показывается. Кастомизация `WixUI_InstallDir.MaintenanceTypeDlg` потребовала бы:
- Override встроенного UI fragment WixUIExtension (рискованно — может конфликтовать с Tauri-generated main.wxs).
- Не сработала бы для основного канала запуска (ARP), только для повторного запуска .msi.

**Выбранный путь — галочка в самом приложении**:
- UI с галочкой показывается в Settings → «Опасная зона» → «Удалить программу» (там же, где `Перенастроить бота`).
- Tauri-команда `request_uninstall(delete_user_data)` спавнит `msiexec /x` с MSI public property `DELETE_USER_DATA=1`.
- WiX-фрагмент содержит CustomAction, который читает свойство и при `=1` чистит `%APPDATA%\GridScalp\` до RemoveFiles.

Преимущества: работает всегда (UI всегда полный, не зависит от WiX UI mode), surgical (не трогает Tauri-generated main.wxs), безопасный default (без галочки данные сохраняются, как и при любых других сценариях uninstall).

## Что сделано

1. **WiX-фрагмент** `desktop/src-tauri/installer/cleanup.wxs`:
   - `Property DELETE_USER_DATA` default=`0`, `Secure="yes"` (нужно для deferred CA).
   - `CustomAction GridScalpRemoveUserData`: `Execute="deferred"`, `Impersonate="yes"` (чтобы `%APPDATA%` указывал на профиль пользователя, а не SYSTEM), `Return="ignore"` (best-effort), ExeCommand=`powershell.exe ... Remove-Item -LiteralPath $env:APPDATA\GridScalp -Recurse -Force -ErrorAction SilentlyContinue`.
   - `InstallExecuteSequence`: `<Custom Action="..." Before="RemoveFiles">REMOVE="ALL" AND DELETE_USER_DATA="1"</Custom>`.
   - `ComponentGroup GridScalpUserDataCleanup` (anchor с пустым Component+CreateFolder) — нужен, чтобы Tauri через `componentGroupRefs` притянул весь фрагмент в линкер; иначе Property+CA+IES молча выпадают из MSI.

2. **`tauri.conf.json`** — `bundle.windows.wix`: добавлены `fragmentPaths: ["./installer/cleanup.wxs"]` + `componentGroupRefs: ["GridScalpUserDataCleanup"]`.

3. **Rust-модуль** `desktop/src-tauri/src/uninstall.rs`:
   - `UPGRADE_CODE` константа, совпадает с tauri.conf.json (инвариант — обновлять оба).
   - `find_product_code()`: вызывает PowerShell `WindowsInstaller.Installer.RelatedProducts(UPGRADE_CODE)` → возвращает ProductCode в фигурных скобках. Без новых крейтов (винrt/windows-sys в Cargo.toml не добавлял).
   - `#[tauri::command] request_uninstall(delete_user_data: bool)`: спавнит `msiexec.exe /x {ProductCode} DELETE_USER_DATA={0|1} /qb` с флагами `CREATE_NO_WINDOW | DETACHED_PROCESS`. `/qb` — basic UI (только progress), потому что подтверждение пользователь уже дал в нашем диалоге.

4. **`lib.rs`**: `mod uninstall;` + `uninstall::request_uninstall` в `invoke_handler!`.

5. **UI** `desktop/src/components/SettingsModal.tsx`:
   - В «Опасной зоне» добавлена вторая кнопка «Удалить программу» рядом с «Перенастроить».
   - Вложенный `Modal` (nested внутри SettingsModal) с `Checkbox` «также удалить все мои данные и настройки» (default OFF) + `Alert` color="red" при выбранной галочке (про возможные сторонние программы с тем же именем).
   - При confirm — `invoke("request_uninstall", { deleteUserData })` → `setTimeout(500) → window.close()` (надо закрыть окно, чтобы msiexec не упёрся в Files in Use).

6. **wiki**: создана [[auragrid-msi-uninstall-cleanup]] — концептуальная страница (UX-сценарии, инварианты, поток событий, анти-паттерны, источники).

# 2026-05-25 (третья сессия) — AuraImpulse: концепция новой стратегии замёрзла, методология в vault, ТЗ в репо

## Контекст

Продакт-владелец поставил задачу: добавить в проект новую отличную стратегию, **прежде всего обсудить и доработать концепцию с торговой точки зрения**, далее перейти к реализации. Концепция: импульсная стратегия (MVP без индикаторов), pending-ордера на дистанции «аномальной волатильности», захват только при импульсе, после срабатывания — сразу SL + обычный трейлинг профита Ауры.

PHASE 1 открыл: [[runbook-vault-integration]], [[auragrid]] MOC, [[auragrid-trading-core]], [[auragrid-trading-settings]], [[adr-002-trail-rework-mq5-parity-departure]], journal `2026-05-24.md` и обе ранние сессии `2026-05-25.md`. Контекст замеренных параметров текущей Ауры (38 полей) — полностью в голове.

## Что сделано: 4 раунда уточнения концепции

Концепция эволюционировала через диалог. Каждый раунд — пользователь правит → я подсвечиваю скрытые вопросы → следующая итерация.

1. **Раунд 1.** Я предложил 5 ключевых развилок: метод расчёта «аномальной волатильности» (4 варианта), «импульс = дистанция или ещё и скорость», «оба pending параллельно или нет», набор заимствованных vs новых настроек, отдельный preset-type vs режим.
2. **Раунд 2 (правки пользователя).** «Аномальная волатильность» → просто параметр `first_step` в pts (никакой rolling-stat). Скорость импульса → не важно, MVP. **Pending'и НЕ параллельны:** при срабатывании одного оппозитный снимается; новые pending только после закрытия. **Новый параметр `cooldown_sec`** (пауза после закрытия). Выбрал отдельный preset-type.
3. **Раунд 3 (правки пользователя).** Активацию трейлинга по двум USD-параметрам (`profit_fixing_direction` + `auto_calculated_profit`) → заменить на **один параметр в pts**. Cooldown — любое закрытие. **Важно:** `sl_distance_pts` (per-trade SL) → заменить на `min_account_balance` (порог equity счёта; ≤ → остановка стратегии).
4. **Раунд 4 (правки пользователя).** `max_loss` → убираем (есть `min_account_balance`). Equity-метрика — подтверждена. **`sl_distance_pts` ВОЗВРАЩАЕТСЯ** (стартовый SL при входе) + `profit_trail_activation_pts` отменён: активация трейла происходит **автоматически по геометрии** когда `(цена − SL) > trail_size_profit + trail_update_distance_profit`. Это унифицирует условие в **одну формулу без отдельной фазы активации**. `min_account_balance` переместить в `general`.

Финальная концепция: 13 полей (4 в `general`, 9 в новой секции `impulse`). State machine: Watching → (срабатывание + снятие оппозитного + стартовый SL) → Trading → Cooldown → Watching. Защита через `min_account_balance` по equity на каждом тике.

Подсветил числовой пример «трейл стартует на первом тике если `sl_distance_pts > trail_size_profit + trail_update_distance_profit`» — пользователь зафиксировал как корректное поведение.

## Fast-path решения (приоритет — скорость)

Приоритет пользователя зафиксирован в двух местах ТЗ § 2.6 говорит «принять решение в реализации»:

1. **Двойная отправка SL.** TZ §2.6: «старт с простого пути (отдельный SLTP). Если в live-тестах окно проявится — переключить на двойную отправку.» Учитывая приоритет скорости+безопасности на gap'ах — сразу выбран **двойная отправка**: `request['sl']` в pending'е (грубая защита = `sl_distance_pts + PRE_FILL_SL_BUFFER_PTS=5 pts`) + точный modify SL после fill (от фактической `position.price_open`). Окно беззащитности = 0.
2. **`_dirty` флаг для persistence.** SQLite UPSERT — дорогая операция (~10μs); на 20Hz тиков без изменений = 200μs/сек впустую. Флаг ставится только при mode/ticket transitions / SL подтяжке; `_save_if_dirty()` пропускает запись если ничего не менялось.

Все остальные fast-path соображения уже в ТЗ §2 (один прокс `positions_get(symbol)` + один `orders_get(symbol)` за тик, фильтр по magic локально, gap-handling в `_find_my_position`, no-op modify check, FSM без лишних branches).

1. **Двойная отправка SL** (pre-fill + точный SLTP) — окно беззащитности = 0. Архитектурно лучшее решение для приоритета скорости.
2. **`_make_pending_refresher` callback для executor.on_retry** — slippage-гигиена в один проход, без перерасстановки FSM.
3. **Детерминированная gap-сортировка** `(time_msc, time, ticket)` — корректный инвариант «ровно одна позиция».
4. **`isinstance`-диспатч** вместо рефакторинга `Engine` — Surgical (ADR-001), нулевой риск регрессии в AuraGrid.
5. **Symmetric `extra="forbid"`** обоих моделей — нельзя случайно смешать секции.
6. **Унификация UX-сигнала** `get_status.max_loss_hit = state.stopped` + `handle_reset_stopped` алиас → одна кнопка в UI независимо от type.
