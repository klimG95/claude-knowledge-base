## Что выучили (Prevention уроки)

- Любая операция close-multiple должна освежать tick per-item + передавать `on_retry` callback
- `normalize_lot` тесты должны включать `volume_step ≠ 0.01`
- `engine.start()` всегда сверяет состояние с MT5 перед `running=True`
- UI labels не должны указывать единицы, которых нет в коде
- Билд тестировщика **обязательно** сверять с git HEAD before deploy
- **Симптом ≠ root cause. Гипотезу подтверждай реальными retcode из логов, не предполагай.**
- **Counter успехов должен отражать реальность, а не return value executor'а.** SL/TP race часто закрывает позицию параллельно — это надо учитывать через re-verify `positions_get(ticket=…)`.
- **Snapshot/restore паттерн** для любого state, изменяемого до `execute()`. Иначе drift копится тихо.
- **`updated == 0` двусмысленен.** Различай «нечего менять» vs «ничего не сделалось».
- **vault-workflow реально окупается.** Ре-аудит был запущен только потому что пользователь применил новый workflow. Без него — релиз ушёл бы с S1 нерешённым.

### Раунд 3 — три UX-улучшения: close-as-trail, pause-keeps-trailing, file presets

Пользователь сформулировал три задачи, все три закрыты в одной сессии.

**Задача 1 — Close All / Close Buy / Close Sell как «арм трейлинга».**
Семантика IPC `close_channel`/`close_all` изменена: вместо мгновенного physical-close (TRADE_ACTION_DEAL по каждой позиции) теперь выставляется SL = bid/ask − `adjusted_stops_level × point` (как при достижении target profit) и фиксируется `state.trail_sl`. Дальше стандартный `profit_trailer.manage()` подтягивает SL по `trail_update_distance_profit`. Если цена откатится — позиции закроются по SL, если пойдёт в плюс — SL ползёт. Реализация:
- `ProfitTrailer.arm_manual(state)` (новый публичный метод) — порт логики ветки «А» из `manage()`, возвращает `ArmResult.{NONE,ARMED,ALREADY_ACTIVE}`. Защищён от двойной активации (`state.trail_sl != 0` → no-op).
- `Protection.arm_channel_trail(state, profit_trailer)` (новый метод) — wrapper, после ARM удаляет pending-ордера канала и сбрасывает `state.pending_ticket = 0` (паттерн ветки ACTIVATED в `engine.process_channel`).
- `handle_close_channel`/`handle_close_all` (IPC) — переключены на `arm_channel_trail`. В `CloseResult` добавлено поле `armed_trail: bool` (default False, для backward-compat), UI отображает соответствующий текст.
- UI: модалки подтверждения в `StrategyPanel.tsx` и `ChannelCard.tsx` переписаны — «На все позиции будет выставлен SL на текущей цене, дальше трейлинг по параметрам сетки. Цена в плюс → SL подтянется; откат → закроется по SL».

**Задача 2 — пауза останавливает только открытие новых сделок.**
В `engine.process_channel` guard `if state.paused: return` перенесён с самого начала на середину — между блоком 3 (profit_trailer.manage) и блоком 4 (SCALP→CG transition). Теперь на паузе продолжают работать: детекция новых позиций (1), reset после full close (2), partial-close sync (2b), stale pending sync (2c), profit-trailing (3). Блокируются: переход SCALP→CG (4) и dispatcher по режиму (5, новые ордера/добор).
- Тест `test_01_paused_channel_is_noop` переименован в `test_01_paused_channel_blocks_new_orders_but_keeps_trailing` и обновлены ожидания: place_first/grid/trail_pending/cg.process/transition_from_scalp — НЕ вызываются; profit_trailer.manage — вызывается 2 раза (BUY+SELL).

**Задача 3 — Save/Load пресета как отдельный yaml-файл.**
- `strategies::export_preset(magic, dest_path)` (Rust) — читает `<APPDATA>/GridScalp/strategies/<magic>.yaml`, исключает `license_key`/`bot_version`/`preset_name`/`config_version`/`ipc`/`licensing`/`log_*`/`general.magic_number`/`mt5.{login,password,server}`, пишет в `dest_path`. Остаются «торговые» секции: `general.{allow_buy,allow_sell,max_loss}`, `scalping`, `conservative_grid`, `notifications`, `mt5.symbol`.
- `strategies::import_preset(magic, src_path)` (Rust) — обратное: читает `src_path`, мержит с существующим `<magic>.yaml` (сохраняя секретные/рантайм-поля), пишет обратно.
- Tauri commands `strategy_export_preset`/`strategy_import_preset` (`lib.rs`); import дополнительно запускает graceful restart бота если он running (паттерн `strategy_apply_params`).
- UI: пункты меню «Сохранить пресет в файл…» / «Загрузить пресет из файла…» в `StrategyPanel.tsx`, file dialogs через `@tauri-apps/plugin-dialog` (добавлен в Cargo.toml + package.json + capabilities `dialog:allow-{save,open}` + `.plugin(tauri_plugin_dialog::init())` в lib.rs).

**Попутный фикс — `start_bot` нарушение контракта.**
В процессе прогона полного pytest suite обнаружен pre-existing failing тест `test_start_bot_returns_already_running_when_engine_up`. Тест ожидал `{ok=false, error=bot_already_running}` при повторном старте (по контракту `docs/contracts/ipc.md` §2.3 и §5). Код возвращал `{ok=true, error=None}` с обоснованием «idempotent для wizard Step4». Проверка: ни в Tauri, ни в UI вызовов `start_bot` нет — гипотеза автора о двойном вызове не подтверждена. Привёл код к контракту: `handle_start_bot` теперь возвращает `ERR_RESULT_BOT_ALREADY_RUNNING` при `engine.running=True`. Контракт > комментарий-гипотеза.
