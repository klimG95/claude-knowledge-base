# Runbook: аудит подтверждений

Как сократить число запросов на подтверждение, не расширив права. Запускается по триггеру «слишком часто спрашиваешь», «убери подтверждения», «настрой разрешения», а также один раз при онбординге нового проекта — до того, как над ним начнут работать другие чаты.

Ключевой факт, который определяет всю процедуру: **правило в `settings.json` сопоставляется с началом строки команды и не разбирает флаги.** Поэтому оно может разрешить ровно то, что встроенный валидатор Claude Code отклонил бы, и поэтому read-only оценивается по конкретному вызову, а не по подкоманде.

## Prerequisites

- Есть история сессий: `~/.claude/projects/<encoded-cwd>/*.jsonl`.
- Известно, куда писать: `.claude/settings.json` в репо проекта (общий для команды) либо `.claude/settings.local.json` (личный, не коммитится). Не `~/.claude/settings.json` — правило из одного проекта не должно действовать во всех.

## Procedure

1. **Замерить, а не угадать.** Скрипт разбора транскриптов — в `docs/permissions.md` пакета методологии, раздел «Как замерить у себя». Считаются две вещи: распределение вызовов по формам (SIMPLE / COMPOUND / SCRIPT) и строки, повторяющиеся ≥ 3 раз.

2. **Посчитать `Edit` и `Write` отдельно.** Обычно это крупнейшая группа подтверждений, и закрывается она одним `defaultMode: acceptEdits`, а не списком правил. Решение принимает пользователь — это заметное расширение.

3. **Сменить инструмент там, где можно.** Всё, что делалось через `Get-ChildItem` / `Select-String` / `Get-Content` / `node -e`, переводится на Read / Grep / Glob. Они не спрашивают вообще и не расширяют права. Это первый рычаг, а не последний.

4. **Стандартизировать форму запуска** для команд, которые действительно нужны: одна каноническая строка без пайпов и редиректов, записанная в конституцию проекта. Точное правило совпадает, только если строка каждый раз одна и та же.

5. **Добавить правила — узкие.** По одному на конкретный вызов. Перед добавлением каждое проверяется по таблице «что нельзя» ниже.

6. **Ревизия того, что уже лежит в `allow`.** Ищутся две категории: избыточные (команда и так разрешена автоматически) и слишком широкие (wildcard на раннер или на git-подкоманду). Избыточные удаляются — они не убирают подтверждений, а только снимают проверку флагов.

7. **Проверить, что файл валиден** (`ConvertFrom-Json`) и зафиксировать: запись в `journal/`, строка в `CHANGELOG.md`, поведенческое правило — в auto-memory (`feedback_tool_choice_over_shell`).

## Verification

- `settings.json` парсится, `deny` не тронут.
- В `allow` нет ни одного wildcard на интерпретатор, раннер пакетов, task-runner, `git fetch`, `gh api`, `curl` / `wget`.
- В `allow` нет правил на команды, разрешённые автоматически (`ls`, `cat`, `grep`, `git status`, `git log`, `gh pr view`, …).
- Ни одно правило не содержит пайпа, редиректа, `-c key=value` или префикса вида `VAR=x cmd`.

## What NOT to do

- **Не добавлять wildcard ради тишины.** `Bash(npm run:*)` — это запуск любого скрипта проекта, то есть произвольный код. `Bash(git log:*)` — открытый `--output=ФАЙЛ`.
- **Не дублировать автоматически разрешённое.** Пользы ноль, проверка флагов снимается.
- **Не писать правила в user scope** (`~/.claude/settings.json`): история собирается по всем проектам, и правило, выведенное из одного, начнёт действовать во всех.
- **Не трогать `deny` и `ask`** в рамках этой процедуры — пользователь настроил их намеренно, и `deny` сильнее `allow`.
- **Не считать «скрипт отработал» проверкой.** Правило считается рабочим, когда команда в канонической форме прошла без запроса; см. парную проверку в `[[runbook-troubleshooting]]`, если он заведён в проекте.

## Rollback

`settings.json` версионируется вместе с репо — откат обычным `git revert` коммита с правилами. Если менялся `defaultMode`, отката одной строки достаточно: удаление `"defaultMode": "acceptEdits"` возвращает поведение по умолчанию немедленно, перезапуск сессии не нужен.
