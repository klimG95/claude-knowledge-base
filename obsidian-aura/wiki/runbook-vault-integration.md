# Runbook — Vault как память проекта (обязательный workflow)

**TL;DR.** Vault — не справка, а **первая и последняя фаза** каждой содержательной задачи. Без чтения vault — нельзя начинать. Без записи обратно в vault — задача не закрыта. Это правило существует, потому что vault полезен только если он живой; справка, которую забывают обновлять, превращается в шум.

## Когда применять

**Всегда**, когда сессия — это содержательная работа по проекту (не разовое «прочти файл», не помощь по командам терминала). Триггеры применения:
- Любая правка кода в репо проекта
- Анализ логов/инцидента
- Архитектурное решение
- Запрос «как работает X» / «почему мы сделали Y»
- Релизный смока, тестирование, ревью

**Не применять** для:
- Команд оболочки и одношаговых утилит
- Вопросов про сам Claude Code / agent SDK / API
- Перевод/форматирование без проектного контекста

## Три фазы каждой задачи

### Фаза 1 — Context (перед содержательным ответом)

Никогда не отвечать «из головы» если в vault может быть запись. Порядок:

1. **Auto-memory** — что я уже знаю про пользователя и проект (загружается автоматически)
2. **`index.md` vault'а** — есть ли страница по теме
3. **MOC проекта** (например, [[auragrid]]) — если работа по конкретному проекту
4. **Конкретные wiki-страницы** — открываю те, что нашлись в шагах 2-3
5. **Последние 1-2 записи `journal/`** — что было в недавних сессиях, что осталось открытым

Только после этого — начинаю работу. В первом текстовом ответе пользователю кратко указываю, какие страницы открыл (1-2 строки, не отчёт).

### Фаза 2 — Work (содержательная работа)

По задаче. В процессе:
- Если узнаю что-то новое → отмечаю мысленно «это пойдёт в wiki/incidents/journal»
- Если решение нетривиальное → готовлю материал на ADR (см. AGENTS правила)
- Если обнаружил противоречие vault vs реальность → исправляю vault (по правилам AGENTS «приоритет за vault как живой источник»)

### Фаза 3 — Capture (перед завершением турна)

Без этой фазы задача **не закрыта**. Минимум:

- **`journal/YYYY-MM-DD.md`** — создать или дополнить запись сессии. Что делали, к чему пришли, что осталось открытым.
- **`<project>-incidents-log.md`** — если был инцидент или диагностика бага
- **wiki-страницы** — обновить/создать, если появилось новое знание о компонентах/решениях/контрактах
- **`CHANGELOG.md`** — короткий пункт о сессии со ссылками на затронутые страницы
- **`index.md`** — если в wiki созданы/переименованы/удалены страницы
- **Auto-memory** — если в сессии появился ссылочный эталон (страница, к которой буду возвращаться) → указатель на неё

Эта фаза — не «опциональный финал», это часть задачи. Если capture не сделан — задача не сделана.

## Пример (anti-template)

❌ **Плохо:**
> User: «Исправь баг с close-all».
> Claude: [читает код, фиксит, коммитит, push].
> Конец.

✅ **Хорошо:**
> User: «Исправь баг с close-all».
> Claude: «Открыл [[auragrid]], [[auragrid-trading-core]], последний journal. Контекст: ...»
> [читает код, фиксит, коммитит, push].
> «Записал в [[auragrid-incidents-log]] раздел 2026-XX-XX, дополнил [[auragrid-trading-core]] анти-паттерном про tick refresh, journal/2026-XX-XX.md создан. Auto-memory: указатель на trading-core добавлен.»

## Когда сократить

В малой задаче (одно изменение, ясный контекст) фазы могут быть короткими:
- Context: одна-две строки «открыл [[X]], [[Y]]»
- Capture: одна-две строки «обновил [[X]], journal — добавил пункт»

Но не нулевыми. Нулевая фаза = vault мёртв.

## Когда capture-фаза значительна

- Инцидент с диагностикой — отдельный раздел в incidents-log по [[templates/template-incident]]
- Архитектурное решение — отдельный ADR `wiki/adr-NNN-...md` по [[templates/template-adr]]
- Новый компонент / контракт — отдельная wiki-страница

В этих случаях capture может быть половиной общего времени сессии. Это нормально — это инвестиция в будущие сессии.

## Анти-паттерны

1. **«Не нашёл в vault → значит вопрос новый»** — нет, возможно vault неполон. Если по логике в vault **должна** быть запись, но её нет — это сигнал создать страницу, а не пропустить контекст.
2. **«Сделаю запись потом»** — не сделаешь. Capture-фаза только в той же сессии, иначе теряется свежесть.
3. **«Это слишком мелко для записи»** — если пользователь сказал что-то нетривиальное про проект, или ты разобрался в неочевидной части — это материал. Не откладывать.
4. **«Только journal, без incidents/wiki»** — journal — хронология, wiki — структура. Если инцидент — он в incidents-log даже если короткий. Journal содержит **указатель** на запись инцидента, не дублирует.
