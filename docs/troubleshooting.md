# Troubleshooting

Решения типичных проблем при установке и работе с claude-knowledge-base.

## Symlink не работает (Windows)

### Симптом

`install.ps1` падает с ошибкой «You do not have sufficient privilege» или `mklink` пишет «отказано в доступе». Файл `<install-dir>/AGENTS.md` отсутствует или не открывается из корня.

### Причина

Создание symlink на Windows требует прав Administrator или включённого Developer Mode. По умолчанию обычный пользовательский сеанс не имеет этих прав.

### Решение

Вариант 1 — запустить PowerShell от имени администратора:

```powershell
Start-Process pwsh -Verb RunAs
cd <install-dir>
./install.ps1
```

Вариант 2 — включить Developer Mode (Settings → For developers → Developer Mode), после этого `mklink` работает без admin.

Вариант 3 (fallback без symlink) — скопировать AGENTS.md вместо symlink:

```powershell
Copy-Item obsidian-aura/AGENTS.md AGENTS.md
```

Минус: правки в `obsidian-aura/AGENTS.md` не отражаются в корневой копии автоматически. Нужно синхронизировать вручную после каждого изменения конституции.

## Symlink сломался после переноса папки

### Симптом

После переноса/переименования install-директории `AGENTS.md` в корне открывается как пустой файл или указывает на несуществующий путь.

### Решение

Symlink на Windows хранит **абсолютный** путь. После переноса — пересоздать:

```cmd
del AGENTS.md
mklink "<new-install-dir>\AGENTS.md" "<new-install-dir>\obsidian-aura\AGENTS.md"
```

Команда требует Administrator.

## Claude не подгружает auto-memory

### Симптом

Claude задаёт базовые вопросы про язык, автономность, текущий проект — те, что должны быть в auto-memory. Создаётся ощущение, что агент пришёл с нуля.

### Проверка пути

Auto-memory живёт в `~/.claude/projects/c--<encoded-path>/memory/`, где `<encoded-path>` — текущая рабочая директория с заменой `\` и `/` на `-` и `:` опущенным.

Пример для `c:\Users\Administrator\Desktop\my-vault\`:

```
~/.claude/projects/c--Users-Administrator-Desktop-my-vault/memory/MEMORY.md
```

### Решение

1. Проверить существование папки `memory/` по правильному пути.
2. Проверить наличие `MEMORY.md` — индексного файла со ссылками на остальные memory-страницы.
3. Если auto-memory создавалась для одного пути, а Claude запущен из другого — папка не подхватится. Запустить Claude из правильной директории.
4. Если установка была через `auto-memory-templates/*.example` — переименовать в живые имена (убрать `.example`) и положить в правильную `memory/`-папку.

## Claude задаёт базовые вопросы про язык/автономность

### Причина

Auto-memory не подгрузилась или не содержит соответствующих файлов (`user_language.md`, `feedback_technical_autonomy.md`).

### Решение

1. Проверить путь auto-memory (см. предыдущий раздел).
2. Проверить содержимое `MEMORY.md` — должен ссылаться на `user_language.md` и `feedback_technical_autonomy.md`.
3. Если файлов нет — создать из `auto-memory-templates/*.example` с кастомизацией под пользователя.

## Dataview не рендерит запросы

### Симптом

В Obsidian вместо динамических таблиц (например, индекс ADR в `methodology-overview.md`) видны обычные markdown code-блоки с текстом запроса.

### Решение

Dataview — community plugin Obsidian, не входит в дефолтную поставку. Установить:

1. Obsidian → Settings → Community plugins → Browse.
2. Найти «Dataview» (автор: blacksmithgu).
3. Install → Enable.
4. Закрыть/открыть страницу с запросом — таблица должна отрендериться.

Если плагин установлен, но не рендерит:
- Проверить, что Community plugins включены вообще (Settings → Community plugins → Turn on).
- Проверить, что в код-блоке указан язык `dataview` (lowercase), не `Dataview`.
- Проверить frontmatter страниц-источников: запросы фильтруют по полям, которых может не быть.

## Битые wikilinks после массовой правки

### Симптом

После переименования или удаления страниц в `wiki/` ссылки `[[old-name]]` остались в других файлах. Obsidian подсвечивает их красным; навигация ломается.

### Решение

Grep по vault на удалённое/переименованное имя:

```powershell
Select-String -Path "obsidian-aura/wiki/*.md" -Pattern "\[\[old-name\]\]"
```

Каждое найденное вхождение — исправить вручную: либо удалить ссылку, либо заменить на новое имя.

Превентивная мера — при переименовании страниц делать это через Obsidian (он автоматически обновляет ссылки), а не через файловую систему.

## Параллельные агенты переписали один и тот же hub

### Симптом

После волны параллельных агентов hub-страница содержит мешанину из ссылок разных агентов, дубли разделов, потерянный контент одного из агентов.

### Причина

Нарушено правило «один файл — один агент в волне» (см. `docs/workflows.md §Параллельные агенты`). Два агента одновременно делали Write в один файл.

### Решение

1. **Восстановить из git** — `git checkout HEAD~1 -- <hub-file>` или `git revert` коммита агентов.
2. **Перепланировать** — hub-страницы обновляются только главным агентом в reviewer pass, не sub-agent'ами.
3. **Зафиксировать правило** в `<project>-AGENTS.md` или в ADR, описывающем wave-процесс.

## Конфликт ADR-007 шаблона и обновлённого vault

### Симптом

Методология в рабочем vault'е эволюционировала (новые правила, шаблоны, концепции), а distribution-пакет `claude-knowledge-base` всё ещё содержит старую версию. При установке на новой машине пользователь получает устаревший шаблон.

### Решение

1. **Bump VERSION пакета.** Например, `0.1.0` → `0.2.0` (minor — новые фичи, breaking совместимость с существующими установками) или `0.1.0` → `0.1.1` (patch — фиксы без изменения схемы).
2. **ADR в vault.** Создать `wiki/adr-NNN-claude-knowledge-base-vNNN-sync.md` с разделами:
   - Какие изменения методологии накопились с прошлого bump'а.
   - Какие файлы пакета затрагиваются.
   - Migration plan для существующих установок (если breaking).
3. **Merge правок в `claude-knowledge-base/`** — копирование и generalize-обработка по принципам ADR-007.
4. **Обновление git-репо** — commit + tag = новая VERSION + push.
5. **Уведомление пользователей** — в README пакета указан раздел «обновление до vNNN».

## smoke-test.ps1 падает на проверке отсутствия конкретных имён

### Симптом

`smoke-test.ps1` выводит `[FAIL]` на проверке «нет hardcoded имени реального проекта» в шаблонах или AGENTS.md.

### Причина

Generalize-операция (см. ADR-007) пропустила вхождение конкретного имени реального проекта или владельца репо. Шаблон должен быть полностью обезличен.

### Решение

1. Grep по `claude-knowledge-base/obsidian-aura/` на запрещённые имена.
2. Заменить вхождения на placeholder'ы (`<project>`, `<owner>`, `../<project>/`).
3. Перезапустить `smoke-test.ps1` — должен пройти.

## .ps1 не запускается: «The string is missing the terminator»

### Симптом

`install.ps1` или `smoke-test.ps1` падает пачкой синтаксических ошибок, причём указанная строка выглядит корректной. В сообщении мелькают последовательности вида `вЂ”`.

### Причина

Windows PowerShell 5.1 читает `.ps1` как ANSI, если в файле нет BOM. UTF-8 текст при этом разваливается: длинное тире `—` (E2 80 94) превращается в три символа CP1251, второй из которых — типографская кавычка `”`. PowerShell считает её закрывающей кавычкой строки, и дальше парсер рассинхронизирован — ошибки указывают на строки много ниже настоящей причины.

Достаточно одного не-ASCII символа в комментарии, чтобы скрипт перестал запускаться. Скрипт с русскими сообщениями без BOM не работает вообще.

### Решение

1. Пересохранить файл как **UTF-8 with BOM** (первые три байта `239 187 191`):

   ```powershell
   $p = '.\smoke-test.ps1'
   $txt = [System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))
   [System.IO.File]::WriteAllText($p, $txt, [System.Text.UTF8Encoding]::new($true))
   ```

2. Проверить: `smoke-test.ps1` группа «Кодировка .ps1» ловит это автоматически — и отсутствие BOM, и сам факт синтаксической ошибки.

3. **BOM добавлять только в `.ps1`.** В `.sh` он ломает shebang: строка `#!/usr/bin/env bash` перестаёт распознаваться.

### Как найти причину в чужом скрипте

```powershell
$txt = [System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))
[regex]::Matches($txt, '[—–“”‘’]').Count   # опасные символы при ANSI-чтении
```

## Claude спрашивает подтверждение почти на каждую команду

### Симптом

Профиль разрешений развёрнут, правила в `.claude/settings.json` есть, но подтверждения продолжаются.

### Причина

Правило сопоставляется с **началом строки команды** и не разбирает флаги. Команда вида `$root = "..."; Get-ChildItem ...` начинается с присваивания, а `powershell -File .\check.ps1 | Select-Object -Last 12` — содержит пайп. Ни то, ни другое не совпадёт с правилом, каким бы правильным оно ни было.

На замеренном проекте простыми одиночными командами были 10 вызовов из 373; один и тот же скрипт запускался 19 раз в 18 разных формах.

### Решение

По порядку, а не выборочно:

1. **Сменить инструмент.** Read / Grep / Glob не спрашивают вообще и покрывают почти всё, ради чего пишутся `Get-ChildItem`, `Select-String`, `Get-Content`, `node -e`.
2. **Проверить `Edit` / `Write`.** Если подтверждения в основном на правки файлов — это `defaultMode: acceptEdits`, а не список правил.
3. **Стандартизировать форму запуска** нужных скриптов: одна каноническая строка без пайпов и редиректов, записанная в конституцию проекта.
4. **Добавить узкое правило** — и только теперь.

Полная методика с замером — [permissions.md](permissions.md), процедура для агента — `[[runbook-permission-audit]]` в vault.

### Чего не делать

Не расширять правило до `Bash(npm run:*)`, `node:*`, `npx:*`, `git log:*`, `gh api:*`, `curl:*`. Это эквивалент разрешения произвольного кода, а в случае `git log:*` ещё и бесполезно: read-only git Claude Code разрешает сам, с проверкой флагов.
