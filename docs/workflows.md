# Workflows claude-knowledge-base

Пошаговые типичные сценарии работы агента в vault'е. Для определения понятий — `docs/concepts.md`; для playbook'а кастомизации — `AGENT-MANUAL.md`.

## Обработка raw/ материала

### Триггеры пользователя

- «обработай»
- «обработай новый файл»
- «разнеси то, что я положил в raw»
- упоминание появления нового файла в `raw/`

### Шаги

1. **Read raw-файл целиком.** Не выборочно, не по фрагментам. Если файл большой — читать по частям до полного покрытия.
2. **Выделение сущностей.** Каждая отдельная концепция, человек, проект, продукт, источник, тезис — потенциальная страница в `wiki/`.
3. **Создание или обновление wiki-страниц.** Для каждой сущности: новая страница (если ещё нет) или обновление существующей. Имена файлов — kebab-case, латиница предпочтительнее.
4. **Frontmatter.** Каждая новая страница получает минимальное ядро (`type/tags/created/updated`) плюс расширения по типу.
5. **Двусторонние ссылки.** Если A упоминает B — `[[B]]` в `## Связано с` секции A, и `[[A]]` в `## Связано с` секции B. Никогда односторонних связей.
6. **Маркер processed.** В начало raw-файла добавляется `<!-- processed: YYYY-MM-DD -->`. Если маркер уже есть — дата обновляется. Файл из `raw/` никогда не удаляется и не перемещается.
7. **Обновление index.md.** Каждая новая страница регистрируется в подходящем разделе оглавления с одной строкой описания.
8. **Запись в CHANGELOG.md.** Краткая строка сверху: «обработан `raw/<file>`, созданы `[[a]]`, `[[b]]`, обновлены `[[c]]`».

### Что НЕ делать

- Не удалять и не переименовывать файлы в `raw/`.
- Не дублировать факт в нескольких страницах (выбрать одну каноническую, остальные — `[[ссылки]]`).
- Не пропускать обновление index.md (это разрушает навигацию).
- Не отвечать «обработано» без реальных Write'ов.

## Создание ADR

### Когда

Нетривиальное техническое решение с долгосрочными последствиями или любое каскадное изменение методологии. См. `docs/concepts.md §ADR`.

### Триггеры пользователя

- «зафиксируй решение»
- «это решение»
- «архитектурно так»
- «измени Y в методологии» (если Y касается формата/конвенций)

### Шаги

1. **Определить следующий свободный adr_id.** Поиск максимального `adr_id` в существующих `adr-NNN-*.md`, +1.
2. **Имя файла:** `wiki/adr-NNN-short-kebab-name.md`.
3. **Заполнить шаблон** `templates/template-adr.md`: frontmatter + Context + Considered options (минимум 2) + Pre-flight checks + Decision + Migration plan (если каскад) + Verify + Consequences + Связано с + Источник.
4. **Status = proposed** при создании. После исполнения decision — изменить на `accepted`.
5. **Зарегистрировать в index.md** в разделе ADR или MOC соответствующего проекта.
6. **Двусторонние ссылки** на смежные ADR (предыдущий каскад, родительское решение, superseded).
7. **Запись в journal и CHANGELOG.**

## Запись инцидента

### Триггеры пользователя

- «зафиксируй инцидент»
- «у нас инцидент: ...»
- «упало в проде»

### Шаги (дефолт — раздел в общем incident-log)

1. **Найти `<project>-incidents-log.md`** или создать (если первый инцидент проекта).
2. **Добавить раздел** по структуре `templates/template-incident.md`:
   ```
   ## YYYY-MM-DD severity=<low|med|high|crit> — <короткое имя>
   ```
3. **Заполнить поля:** Симптом, Диагноз, Лечение, Корневая причина, Follow-up.
4. **Двусторонние ссылки** на компонентные страницы и domain-hub соответствующего домена.
5. **Обновить frontmatter `updated:`** в incident-log.
6. **Запись в journal и CHANGELOG.**

### Когда отдельный файл, а не раздел

Только если инцидент становится ссылочным эталоном: на него опираются ADR, runbook'и или другие инциденты неоднократно. Иначе — раздел.

## Создание runbook

### Триггеры пользователя

- «сделай runbook для X»
- «давай пропишем процедуру»
- «как мы это делаем, зафиксируй»

### Шаги

1. **Имя:** `wiki/runbook-<short-kebab-name>.md`.
2. **Шаблон** `templates/template-runbook.md`: frontmatter (`type: runbook`, `automation_status:`) + Prerequisites + Procedure + Verification + What NOT to do + Rollback + Связано с + Источник.
3. **Procedure** — нумерованный список атомарных шагов. Каждый шаг должен быть однозначным.
4. **Verification** — конкретные проверяемые признаки.
5. **Ссылка из соответствующего MOC** на новый runbook.
6. **Запись в journal и CHANGELOG.**

## Закрытие сессии (финальный sweep)

### Триггеры пользователя

- «закрой сессию»
- «закрой спринт»
- «зафиксируй сделанное»
- «подведём итоги»

### Шаги

1. **index.md.** Если в `wiki/` что-то создавалось или менялось содержательно — оглавление обновлено.
2. **journal/YYYY-MM-DD.md.** Создать или дополнить записью текущей сессии: что делали, к чему пришли, что осталось открытым.
3. **CHANGELOG.md.** Запись сверху: список затронутых страниц с краткими описаниями. Записи идут от новых к старым.
4. **Auto-memory.** Если появились новые ссылочные эталоны — обновить указатели. Формат: «по теме X эталонные страницы — `[[a]]`, `[[b]]`».
5. **Битые `[[ссылки]]`** — Grep по vault на имена удалённых/переименованных страниц. Найденное — исправить.
6. **Frontmatter `updated:`** — на всех содержательно правленных страницах.

## Ревизия / аудит методологии

### Триггеры пользователя

- «проверь всё»
- «ревизия»
- «аудит методологии»

### Шаги

1. **Glob по `obsidian-aura/wiki/`** — полный список файлов; сверить с разделами `index.md`. Orphan-страницы (не упомянуты в index) — добавить или исключить.
2. **Grep всех `[[wikilink]]`-целей** → сравнить с короткими именами файлов. Битые ссылки — исправить или удалить.
3. **Read AGENTS.md.** Проверить согласованность правил, отсутствие противоречий, покрытие триггеров.
4. **Auto-memory против vault.** Пройти по `MEMORY.md` и memory-файлам; найти устаревшие или дублирующие vault записи. Дубли — сократить до указателей.
5. **Применить точечные правки** в этой же сессии. ADR — только если ревизия выявила каскадное изменение.
6. **Запись в `journal/YYYY-MM-DD.md`** как отдельный раздел сессии с перечнем найденных проблем и применённых правок.

## Параллельные агенты на больших задачах

Большая задача (каскад с >20 файлами, структурная документация нового крупного проекта) — выполняется параллельными агентами через Task tool. Это сокращает время в разы, но требует строгой дисциплины.

### Когда параллелить

| Фаза | Параллелить? |
|------|-------------|
| Skeleton (создание заготовок страниц) | Реже — однопоточно безопаснее, меньше конфликтов |
| Наполнение существующих страниц | Да — каждому агенту непересекающийся набор |
| Reviewer pass | Нет — один агент проверяет всю волну |
| Обновление hub-страниц | Нет — только главный агент после волны |

### Правило «один файл — один агент в волне»

Жёсткое правило. Hub-страницы, в которые сходятся ссылки из подстраниц всех агентов, обновляются **только** в финальном reviewer pass главным агентом — не sub-agent'ами параллельной волны. Иначе race-conditions на Write.

### Reviewer pass

После каждой волны главный агент:
- Grep `_TBD` (плейсхолдеры из шаблонов) — на отсутствие незаполненных секций.
- Проверка битых wikilinks — Grep по vault на ссылки, ведущие на несуществующие имена.
- Spot-check 2-3 страниц на соответствие шаблону и фактическую точность.
- Обновление hub-страниц по результатам волны.

### Передача контекста sub-agent'у

Каждому sub-агенту в его prompt передаются:

1. **Контекст проекта** (1-2 абзаца). Что за проект, какая задача, что уже сделано.
2. **Конкретные файлы.** Полные пути файлов, которые этот агент создаёт/правит. Полные пути источников, которые он читает.
3. **Жёсткие правила.**
   - Не выдумывать факты — только из указанных источников.
   - Плейсхолдеры (`_TBD_`) для незаполненного, не выдуманное содержимое.
   - Минимум N wikilinks в `Связано с`.
   - Frontmatter обязателен.
   - Запрет на правку файлов вне своего набора.
4. **Формат ответа.** Одна строка с подтверждением вида «Агент X: создано N файлов». Это упрощает reviewer pass.

### Анти-паттерны

- Sub-agent правит hub-страницу → race condition с другим sub-agent'ом или reviewer'ом.
- Sub-agent читает посторонние файлы для контекста → расход контекста, нестабильность.
- Sub-agent создаёт страницы, не упомянутые в его mandate → выходит за scope, ломает reviewer pass.
- Reviewer пропускает spot-check → плейсхолдеры протекают в production-состояние vault'а.
