# Кастомизация vault под проект

Документ расширяет `BOOTSTRAP.md` и `AGENT-MANUAL.md`. Покрывает кастомизацию vault'а под конкретный проект **в continuous-режиме** — не только в первой сессии, но и по мере роста проекта.

Целевая аудитория — ты, Claude. Этот файл читается, когда ты сталкиваешься с задачей выходящей за стандартные триггеры конституции и нужно решить: как расширить методологию под текущий проект.

## Что значит «под проект»

Базовая методология `claude-knowledge-base` — project-агностична: 3 слоя памяти, ADR/runbook/incident workflow, 9 шаблонов страниц, правила обработки `raw/`, frontmatter-схема. Эти правила одинаковы для любого проекта.

«Кастомизация под проект» — это всё, что добавляется поверх:

1. **Project MOC** — единая точка входа для всего, что относится к проекту (см. ниже).
2. **Раздел «Работа над проектом X» в `AGENTS.md`** — операционные принципы конкретно для этого проекта (где код, как vault связан с репо, какие принципы для ADR именно здесь).
3. **Расширения frontmatter** — дополнительные поля под проектные оси навигации (компонент, слой, домен, форма страницы).
4. **Agent-first структурный паттерн** — для крупных проектов (>5 компонентов) применяется skeleton + waves подход (см. ниже).
5. **Reading map** — если у проекта свой репо со своим AGENTS.md, в нём добавляется таблица «ситуация → какие страницы vault открывать».
6. **Project-specific auto-memory** — указатели на ключевые vault-страницы проекта.

Кастомизация — итеративный процесс. На bootstrap создаётся скелет; наполнение происходит по мере появления знаний о проекте.

## Когда добавлять project MOC vs расширять существующий

**Создавать новый MOC:**
- Это первый раз, когда проект упоминается в работе с пользователем.
- Проект — самостоятельная единица (своя кодовая база, свои контракты, свой контекст), а не подпроект существующего.
- Имя проекта однозначно идентифицирует тему (не дублирует существующий MOC под другим углом).

**Расширять существующий MOC:**
- Тема — подпроект / модуль / интеграция уже существующего проекта (например, новый клиент того же продукта).
- Появился новый аспект работы (analytics-direction внутри основного продукта).
- Тема покрывается одним из существующих domain-hub'ов.

**Граница субъективна.** Лучшая эвристика — посмотреть на frontmatter будущих страниц: если все они логично получают одинаковый набор тегов уже существующего MOC — расширяй существующий. Если тегов и базовых атрибутов недостаточно — новый MOC.

## Расширения frontmatter под крупные проекты

Базовое ядро frontmatter (по ADR-005-аналогу в vault'е):

```yaml
---
type: <concept|entity|source|adr|runbook|moc|...>
tags: [tag1, tag2]
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

Для крупного проекта добавляй опциональные поля. Паттерн, ранее применённый в реальном проекте (см. ADR-006-аналог в готовом vault):

```yaml
---
type: concept | moc
tags: [<project>, <component>, <layer>, <domain>]
component: <зеркало структуры репо: bot | server | desktop | admin | infra | cross>
layer: kernel | integration | ui | ops | contract | concept
shape: concept | reference | contract | domain-hub | inventory
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

- **`component`** — компонент кодовой базы. Зеркалит верхний уровень репо (`python/bot/` → `bot`, `server/` → `server`).
- **`layer`** — слой ответственности (ядро бизнес-логики / интеграция с внешним / UI / ops / контракт / концепция).
- **`shape`** — форма страницы (см. 5 типов ниже). Не пересекается с `type` — `type` остаётся стандартным (`concept`/`moc`/...), `shape` — проектная ось.

Эти поля **не вводятся как обязательные** через каскад. Они опциональные расширения для Dataview-фильтрации.

**Когда добавлять поля:** когда проект достигает уровня, где Dataview-запросы по этим осям дают полезные срезы (минимум 5-10 страниц по оси, чтобы фильтр был полезен).

## Когда применять agent-first структурную документацию

Этот паттерн — крупный, накладной, разово окупающийся. Применяется не каждому проекту.

### Триггер

Применять, если выполняются **все** условия:
- Проект имеет **>5 исполняемых компонентов** с нетривиальной внутренней логикой.
- Проект достиг **предрелизного или production-объёма** (не early prototype).
- Есть **cross-cutting домены** (licensing, logging, telemetry, packaging) — пересекающие компоненты, которые сложно охватить иерархией.
- Пользователь явно подтвердил, что хочет полную карту (это большая работа на ~5 сессий, нужен договор).

Если хоть одно условие не выполнено — лёгкая версия: project MOC + страницы по мере появления знаний, без waves и без 5 типов страниц.

### 5 типов страниц

При полном применении паттерна используются 5 sub-шаблонов (в дополнение к базовым `template-adr` / `template-incident` / `template-runbook` / `template-weekly-review`):

| Шаблон | Shape | Когда применяется | Ключевые секции |
|--------|-------|-------------------|-----------------|
| `template-component.md` | concept | Подсистемы с богатой логикой (core, mt5-integration, analytics) | TL;DR → Когда читать → Идея → Инварианты → Реализация → Контракты → Зависимости → Анти-паттерны → Связано → Источник |
| `template-reference.md` | reference | Мелкие модули (utils, state, tools) | TL;DR → Когда читать → Что делает → Где код → Связано → Источник |
| `template-contract.md` | contract | API / IPC / wire-форматы | TL;DR → Когда читать → Поля → Пример запроса/ответа → Версионирование → Связано → Источник |
| `template-domain-hub.md` | domain-hub | Cross-cutting домены (licensing, logging, telemetry) — мини-MOC по сквозному домену с end-to-end flow | TL;DR → Когда читать → End-to-end flow (Mermaid) → Участники (ссылки на компонентные страницы) → Связано → Источник |
| `template-inventory.md` | inventory | Карты-указатели «артефакт ↔ путь ↔ страница vault» (endpoints, configs, code, tests, state) | TL;DR → Когда читать → Таблица → Связано → Источник |

Ключевая черта всех 5 — **TL;DR + «Когда читать»** в начале. Это снижает количество ненужных Read'ов агентом.

### Skeleton + waves наполнения

Применяется при >30 запланированных страниц. Идея — разделить работу на 2 типа сессий:

1. **Skeleton-проход (одна сессия, один агент).** Создаются все страницы с frontmatter + всеми секциями шаблона, наполнение разделов = плейсхолдеры `_TBD в волне N_`. Параллельно обновляется MOC, hub-страницы, индекс, AGENTS.md. Это однопоточная работа, не параллелится.

2. **Волны наполнения (отдельные сессии, параллельные агенты).** Каждая волна закрывает группу страниц по одному компоненту/домену. Жёсткое правило: **один файл — один агент в волне**. Hub-страницы (которые часто обновляются от нескольких подстраниц) обновляются ТОЛЬКО в финальном reviewer pass волны, не агентами — это исключает race-conditions.

Каждая волна — отдельный ADR-этап с явным migration window. После каждой волны — reviewer pass с критериями «достаточной» детализации:
- Все секции шаблона заполнены без плейсхолдеров.
- Раздел «Реализация» / «Где код» содержит ссылки на конкретные файлы.
- Минимум 5 двусторонних `[[...]]` в «Связано с».
- `updated:` отражает дату волны.

### Параллельные агенты

Распределение работы:
- Один файл — один агент в текущей волне (исключает write-conflict).
- Агенты не знают друг про друга — каждый получает свой непересекающийся набор файлов.
- Hub'ы и MOC — последний reviewer-агент (один, последовательный).
- Перед запуском параллельных агентов — pre-flight чек: список файлов volney, distinct sets, нет пересечений.

### ADR-обвязка

Любая большая структурная работа оформляется как ADR с разделом `Migration plan` (явный перечень файлов и характер правок) и `Verify` (чеклист критериев приёмки). Без ADR — нельзя: каскадные изменения требуют записи «почему мы это делали именно так» для будущих ревизий.

## Как добавить Reading map (если у проекта есть свой репо-AGENTS.md)

Если в репо проекта есть свой `AGENTS.md` (конституция кодовой базы) — в него добавляется раздел **«Reading map»**: таблица «ситуация → какие страницы vault открывать в первую очередь».

Цель: агент, запущенный в папке кода (не в vault), должен знать какую страницу vault'а открыть для текущей задачи.

Структура:

```markdown
## Reading map

| Ситуация | Открыть в первую очередь |
|----------|--------------------------|
| Изменение торговой логики / бизнес-ядра | `<component-core-page>`, `<invariants-page>`, `<lifecycle-page>` |
| Добавление HTTP endpoint | `<inventory-endpoints>`, `<server-routes-page>`, `<contract-openapi>` |
| Изменение IPC | `<contract-ipc>`, `<desktop-rust-page>`, `<bot-ipc-page>` |
| Инцидент с лицензированием | `<cross-licensing-hub>`, `<incidents-log>`, `<licensing-component-page>` |
| Изменение упаковки / релиза | `<cross-packaging-hub>`, `<packaging-specifics-page>` |
| (по мере появления типичных задач — расширять) | ... |
```

Reading map — живой документ. Новые типичные задачи добавляются по мере появления.

## Эволюция auto-memory с ростом проекта

Auto-memory растёт вместе с проектом — но **не дублирует vault**. Правила эволюции:

### Когда добавлять project_*.md

- На bootstrap — создаётся `project_<slug>_context.md` с минимумом: указатель на MOC, локальный путь, GitHub-url.
- При появлении подпроектов / крупных подсистем — отдельные `project_<slug>_<subsys>.md`, если они нужны как точки быстрого доступа (например, `project_<slug>_packaging.md` — специфика релизных процессов, если она часто всплывает).
- При появлении project-specific feedback (не общего user-feedback) — `feedback_<slug>_<тема>.md`. Например, «релизный чеклист после обновления требует <конкретного действия>».

### Когда обновлять указатели

После каждой большой сессии, в которой появились новые **ссылочные эталонные** страницы vault — обнови auto-memory указателями. Триггер: пользователь будет в будущем возвращаться к этой странице как к точке входа.

Например, после создания inventory-страницы по конфигам (`<project>-inventory-configs`) — в `project_<slug>_context.md` добавляется строка «Все configs и env vars → [[<project>-inventory-configs]]».

### Когда сокращать auto-memory

Триггер: страница auto-memory дублирует содержание vault-страницы целиком. Решение — сократить auto-memory до 2-3 строк указателя + ссылка `[[vault-page]]`. Содержание остаётся в vault.

Это часть процедуры «ревизия методологии» / «аудит» (триггер из AGENTS.md). Делается раз в N сессий, не каждый раз.

### Структура memory-файла

Любой добавляемый memory-файл следует шаблону:

```yaml
---
name: <короткое имя>
description: <одна строка для индекса>
type: user | feedback | project | reference
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

<Основной текст: 1-2 абзаца>

**Why:** <почему эта запись существует — какой паттерн поведения / какой контекст>

**How to apply:** <когда и как применять>
```

Структура **Why / How to apply** — критична: позволяет агенту в будущей сессии быстро решить, релевантна ли эта memory текущей задаче.
