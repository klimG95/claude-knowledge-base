# Концепции claude-knowledge-base

Расширенный glossary всех концепций, которыми оперирует методология. Декларативный справочник: что это, когда применять, как структурировать. Для процедурных деталей — `docs/workflows.md`; для playbook'а агента — `AGENT-MANUAL.md`.

## Три слоя памяти

Методология опирается на разделение памяти агента на три независимых слоя. Каждый слой отвечает за свой тип знания и имеет своё место хранения.

### Семантический (vault wiki/)

**Что хранит.** Знания о мире: концепции, факты, источники, термины, связи. Всё, что было захвачено и обработано из `raw/`.

**Где живёт.** `obsidian-aura/wiki/` + `index.md` как оглавление.

**Свойства.**
- Структурирован: каждая страница — одна сущность, одна тема.
- Двусторонние `[[wikilinks]]` образуют граф.
- Версионируется git'ом.
- Источник истины для «что мы знаем по теме X».

### Процедурный (AGENTS.md)

**Что хранит.** Правила работы агента в этом vault'е: как именовать, как обрабатывать, как отвечать, какие триггеры запускают какие процессы.

**Где живёт.** `obsidian-aura/AGENTS.md` (плюс symlink из корня).

**Свойства.**
- Конституция: правила, а не данные.
- При конфликте с любым другим источником — приоритет за AGENTS.md.
- Изменения — через каскадный процесс (отдельная сессия + ADR).

### Эпизодический (auto-memory)

**Что хранит.** Контекст про пользователя и проект: предпочтения, текущая фокусировка, указатели на ключевые страницы vault, история ключевых решений.

**Где живёт.** `~/.claude/projects/c--<encoded-path>/memory/` — за пределами vault.

**Свойства.**
- Переживает рамки одной сессии и одной рабочей директории.
- Содержит **указатели** на vault, не дубликаты.
- При расхождении с vault — приоритет за vault, auto-memory обновляется.

### Связка: когда смотреть какой слой

| Ситуация | Порядок чтения |
|----------|----------------|
| Содержательный вопрос пользователя | auto-memory → `index.md` → конкретные страницы wiki |
| «Как делается X» (процесс) | AGENTS.md |
| «Какие у меня предпочтения» | auto-memory |
| «Что было сделано в прошлый раз» | auto-memory + последняя запись `journal/` |
| «Какая текущая правда о факте Y» | wiki (через `index.md`) |
| «Почему мы выбрали Z» | ADR в `wiki/adr-NNN-*.md` |

**Никогда не сканировать wiki целиком.** Никогда не отвечать «из головы», если в vault есть зафиксированный ответ.

## MOC (Map of Content)

### Что это

Хаб-страница, агрегирующая навигацию по большой теме или проекту. Не содержит знания сама по себе — содержит ссылки на страницы, в которых это знание живёт. Frontmatter: `type: moc`.

### Когда создавать

Триггер: новая тема или проект с >5 связанных страниц wiki, между которыми пользователь будет переключаться. Для одиночных страниц MOC не нужен.

Примеры:
- Большой проект (>20 страниц о коде/архитектуре) → MOC проекта.
- Узкая дисциплина с >5 страницами → тематический MOC.
- Личная база с несколькими доменами → корневой `index.md` плюс отдельные MOC на каждый домен.

### Структура

| Секция | Содержание |
|--------|-----------|
| TL;DR | 1-2 строки: что за тема, зачем хаб |
| Точка входа | Какие страницы открывать первыми по типу запроса |
| Разводка по подтемам | Группировка ссылок: архитектура, контракты, операции, ADR, runbook'и |
| Dataview-индексы | Динамические списки: ADR проекта по статусу, runbook'и, последние обновления |
| Связано с | Ссылки на смежные MOC и общие методологические страницы |

## ADR (Architecture Decision Record)

### Что это

Документ нетривиального решения. Фиксирует контекст, рассмотренные варианты, выбор и его последствия. Цель — пережить переписывания кода: через год вернуться и понять, **почему** так сделано. Frontmatter: `type: adr`, `adr_id`, `status`.

### Когда оформлять

| Триггер | Оформлять как ADR? |
|---------|--------------------|
| Технический выбор с долгосрочными последствиями | Да |
| Каскадное изменение методологии или структуры | Обязательно (см. ниже) |
| Изменение конвенций, шаблонов, схемы frontmatter | Обязательно |
| Точечная правка 1-3 страниц | Нет, обычная правка |
| Bug fix без архитектурных следствий | Нет |
| Реорганизация index.md (слияние/разделение разделов) | Да |

В сомнительном случае предпочесть ADR — это всегда дешевле, чем потом восстанавливать историю мысли.

### Структура

```
## Context           — что мы знали, какие были ограничения
## Considered options — какие пути взвешивались (минимум 2)
## Pre-flight checks — чек-лист проверок зависимостей и блокировок
## Decision          — что выбрали и почему именно этот вариант
## Migration plan    — обязательно для каскадных изменений (этапы)
## Verify            — критерии «решение исполнено корректно»
## Consequences      — положительные, цена, follow-ups
## Связано с         — двусторонние [[ссылки]]
## Источник          — какая сессия, какой контекст
```

**Status переходы:** `proposed` → `accepted` → опционально `superseded` (с полем `superseded_by`) или `deprecated`.

### Pre-flight checks (урок)

Перед началом каскадного исполнения проверь:
- Какие файлы затронуты (явный перечень).
- Нет ли активных блокировок (открытые ADR со статусом `proposed`, незавершённые миграции).
- Технические риски (что ломается, как откатывается).
- Скоуп: ≤30 файлов → одна сессия; >30 → этапы с migration window.
- Wikilinks не страдают (переименования файлов — отдельная подзадача).
- Откат: явный механизм (git revert коммита).

Чек-лист сохраняется в самом ADR — секция `## Pre-flight checks` с галочками.

## Runbook

### Что это

Операционная процедура в формате «предусловия → шаги → проверка → откат». Для повторяющихся операций (релиз, диагностика, инициализация окружения). Frontmatter: `type: runbook`, `automation_status: manual|semi-auto|automated`.

### Структура

| Секция | Содержание |
|--------|-----------|
| Prerequisites | Что должно быть готово до запуска |
| Procedure | Пошаговая инструкция, каждый шаг — атомарный |
| Verification | Признаки успешного выполнения |
| What NOT to do | Анти-паттерны и характерные ошибки |
| Rollback | Как откатить, если что-то пошло не так |
| Связано с | Ссылки на связанные ADR, incident-log, MOC |

### Когда выделять в отдельный файл

- Процедура запускается >2 раз и каждый раз требует одинаковых шагов.
- Процедура требует точной последовательности (отступление → инцидент).
- Процедура запускается человеком вручную или по триггеру пользователя.
- Для одноразовых задач runbook не нужен — достаточно записи в `journal/`.

## Incident-log

### Что это

Журнал инцидентов проекта с диагнозами и решениями. Frontmatter: `type: incident-log`. Цель — накопление паттернов: «когда снова случится X, посмотреть как лечили в прошлый раз».

### Структура

Единый файл `<project>-incidents-log.md` с разделами по дате/severity. Каждый инцидент — секция вида:

```
## YYYY-MM-DD severity=high — <короткое имя>

**Симптом:** ...
**Диагноз:** ...
**Лечение:** ...
**Корневая причина:** ...
**Follow-up:** ...
```

### Когда отдельный файл, а не раздел

Инцидент выделяется в отдельную страницу `wiki/incident-YYYY-MM-DD-*.md` **только** если становится ссылочным эталоном: на него опираются ADR, runbook'и или другие инциденты неоднократно. Дефолт — раздел в общем incident-log.

## Inventory-страницы

### Что это

Карты-указатели по типам артефактов проекта. Не описывают сами артефакты — содержат **таблицу-реестр** с указанием, где артефакт живёт в коде и где описан в vault. Frontmatter: `type: moc`, `shape: inventory`.

Типичные inventory:
- `<project>-inventory-code` — компоненты ↔ путь в репо ↔ страница vault.
- `<project>-inventory-endpoints` — HTTP/IPC endpoints ↔ контракт ↔ реализация.
- `<project>-inventory-configs` — конфиг-файлы ↔ назначение ↔ страница.
- `<project>-inventory-tests` — тестовые сценарии ↔ purpose ↔ путь.
- `<project>-inventory-state` — state-файлы и базы ↔ что хранится ↔ страница.

### Когда создавать

Триггер: проект имеет >10 артефактов одного типа, и агентам нужен общий обзор без множественных Read'ов. Для маленьких проектов inventory не нужны — достаточно ссылок из MOC.

### Структура

| Секция | Содержание |
|--------|-----------|
| TL;DR | Что за реестр, зачем |
| Когда читать | Триггеры обращения (например, «перед изменением endpoint») |
| Таблица-реестр | Строка на артефакт: имя, путь в коде, страница vault, краткое описание |
| Принцип организации | Как реестр сгруппирован (по компоненту, по слою, etc.) |
| Связано с | Ссылки на компонентные хабы и domain-hub'ы |

## Domain hubs

### Что это

Mini-MOC для cross-cutting доменов, проходящих через несколько компонентов. Frontmatter: `type: moc`, `shape: domain-hub`.

Cross-cutting домен — это сквозная ответственность, размазанная по нескольким компонентам кода (licensing, logging, telemetry, packaging, analytics). Domain hub собирает её обратно в единое представление.

### Когда создавать

Триггер: домен затрагивает >2 компонента, и при инциденте/изменении нужно сразу видеть всю цепочку участников.

### Структура

| Секция | Содержание |
|--------|-----------|
| TL;DR | Краткое определение домена |
| Когда читать | Триггеры (инцидент в домене, изменение протокола, новый компонент) |
| End-to-end flow (Mermaid) | Диаграмма прохождения данных через компоненты |
| Участники | Таблица: компонент ↔ роль в домене ↔ страница vault |
| Контракты и инварианты | Ссылки на wire-форматы и общие правила |
| Связано с | Компонентные подстраницы и inventory |

## Reading map

### Что это

Таблица «ситуация → страницы vault для агента». Помогает агенту попасть в правильную точку базы знаний за минимальное число hop'ов. Не отдельная страница методологии — раздел внутри AGENTS.md проекта-владельца кода (если у проекта есть свой репо с собственным AGENTS.md).

### Структура

```
| Ситуация | Открыть в первую очередь |
|----------|--------------------------|
| Изменение торговой логики | <bot-core>, <invariants>, <channel-lifecycle> |
| Добавление endpoint | <inventory-endpoints>, <server-routes>, <contract-openapi> |
| Инцидент в домене X | <cross-X>, <incidents-log>, <X-component> |
```

### Где живёт

В `<project-repo>/AGENTS.md` рядом с кодом. Vault содержит сами страницы; код-репо содержит навигатор по vault'у.

## Frontmatter

YAML-блок в начале каждой страницы wiki. Позволяет Dataview-плагину строить динамические индексы и фильтры.

### Минимальное ядро

```yaml
---
type: <см. список ниже>
tags: [tag1, tag2]
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

Значения `type`:

| Значение | Смысл |
|----------|-------|
| `concept` | концепция, идея, термин |
| `entity` | продукт, модель, инструмент, плагин |
| `source` | внешний источник (статья, репо, видео) |
| `adr` | Architecture Decision Record |
| `runbook` | операционная процедура |
| `incident-log` | журнал инцидентов |
| `moc` | Map of Content / хаб |
| `template` | шаблон страницы |
| `system` | служебная страница методологии |
| `journal` | запись в `journal/` |

### Расширения по типам

| Тип | Дополнительные поля |
|-----|---------------------|
| `adr` | `adr_id: <число>`, `status: proposed\|accepted\|superseded\|deprecated`, опционально `superseded_by` |
| `runbook` | `automation_status: manual\|semi-auto\|automated`, опционально `last_executed: YYYY-MM-DD` |
| `source` | `source_type: article\|book\|video\|podcast\|repo\|web-research\|api-doc`, опционально `source_url` |
| `entity` | `entity_kind: model\|product\|plugin\|tool\|person\|org` |

### Опциональные поля для крупных проектов

При структурной документации большого проекта (паттерн agent-first из реального примера применения — см. `AGENT-MANUAL.md §2`) — добавляются дополнительные поля для Dataview-фильтрации:

| Поле | Значения |
|------|----------|
| `component` | имя крупного компонента проекта |
| `layer` | `kernel\|integration\|ui\|ops\|contract\|concept` |
| `domain` | имя cross-cutting домена |
| `shape` | `concept\|reference\|contract\|domain-hub\|inventory` |

Поля опциональные: вводятся только при необходимости Dataview-фильтров по проекту.

### Когда обновлять `updated`

Обновлять при содержательной правке. Не обновлять при опечатке/выравнивании. В сомнительном случае предпочесть обновление — это критично для Dataview-запросов «что изменилось за неделю».

## Каскадные изменения

### Что это

Изменение, затрагивающее много файлов одновременно. Требует особого процесса — отдельной сессии и ADR с Migration plan.

### Триггеры

| Триггер | Это каскад? |
|---------|-------------|
| Правка AGENTS.md, задающая новое правило | Да |
| Изменение конвенций именования | Да |
| Введение нового обязательного поля frontmatter | Да |
| Изменение шаблона с применением к существующим страницам | Да |
| Реорганизация разделов index.md | Да |
| Правка 1-3 страниц | Нет, обычная правка |
| Bug fix в одной странице | Нет |

### Принципы

| Принцип | Содержание |
|---------|-----------|
| Отдельная сессия | Каскад не смешивается с содержательной работой |
| ADR обязателен | Создаётся перед началом, со статусом `proposed`, обязательная секция `Migration plan` |
| Атомарность | ≤30 файлов — за одну сессию; >30 — этапы с migration window |
| Проверки | Ссылочная целостность; index.md актуален; все целевые файлы обновлены |
| Откат | Через `git revert` коммита каскада. Ручной обратный rewrite не делается |
| Запись | Короткий пункт в CHANGELOG.md + детальная запись в `journal/` |

### Migration plan — структура

```
## Migration plan

### Этап 1 — <имя>
- Затронуто: <список файлов>
- Действия: <конкретные правки>
- Pre-flight: <проверки>

### Этап 2 — <имя>
...
```

Каждый этап атомарный и независимо откатываемый.
