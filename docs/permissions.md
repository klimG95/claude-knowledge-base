# Permissions — как убрать подтверждения, ничего не открыв лишнего

TL;DR: подтверждения вызывает не набор команд, а их **форма**. На замеренном проекте простыми одиночными командами были 10 вызовов из 373 — остальное составные скрипты, которые префиксное правило не покрывает вообще. Поэтому порядок такой: сменить инструмент → стандартизировать форму запуска → и только потом добавить узкое правило.

Базовый профиль и его состав — [`../claude-settings/README.md`](../claude-settings/README.md). Пошаговая процедура для агента — `[[runbook-permission-audit]]` в vault.

## Почему список правил помогает меньше, чем кажется

Замер: 36 транскриптов одного проекта, 373 вызова shell.

| Форма вызова | Доля | Покрывается правилом? |
|---|---|---|
| PowerShell-скрипт (начинается с `$var = ...`, `foreach`, `if`) | 143 | Нет. Правило сопоставляется с началом строки, а строка начинается с присваивания |
| Составная команда (пайп, `&&`, `;`) | 220 | Частично и ненадёжно |
| Простая одиночная команда | **10** | Да |

Второй замер, ещё нагляднее: один и тот же скрипт проверки запускался **19 раз в 18 разных формах** — то абсолютный путь, то относительный, то с `-NoProfile`, то без, то с `| Select-Object -Last 12`. Правило под него в проекте было — и не совпало почти ни разу. Самая повторяемая команда за всю историю встретилась 2 раза.

Вывод: allowlist работает на стабильных формах. Если форма плавает, сначала чинится форма.

## Порядок действий

### 1. Сменить инструмент

Встроенные Read / Grep / Glob не запрашивают подтверждение никогда. Они же покрывают почти всё, ради чего пишутся shell-скрипты:

| Вместо | Использовать |
|---|---|
| `Get-ChildItem -Recurse`, `ls`, `find` | Glob |
| `Select-String`, `grep` | Grep |
| `Get-Content`, `cat`, `head`, `tail` | Read |
| `node -e "..."`, `python -c "..."` для разбора файла | Read + рассуждение, либо Grep |

Это снимает подтверждения и **не расширяет права ни на грамм** — в отличие от любого правила.

### 2. Стандартизировать форму запуска

Для команд, которые агент реально должен запускать (чекеры, сборка, тесты), канонический вид фиксируется в конституции проекта — тогда точное правило совпадает каждый раз:

```
powershell -ExecutionPolicy Bypass -NoProfile -File .\vault-check.ps1 -NoColor
```

Без пайпов и редиректов: `| Select-Object -Last 12` в конце ломает совпадение с правилом.

### 3. Добавить правило — узкое

Точное правило под конкретный вызов лучше одного широкого. Проверка перед добавлением — в следующем разделе.

## Что можно и что нельзя

Ключевой факт: **правило сравнивается со строкой команды по префиксу, без разбора флагов.** У встроенного валидатора Claude Code разбор флагов есть, у правила из `settings.json` — нет. Поэтому правило может разрешить ровно то, что валидатор отклонил бы.

Отсюда — read-only оценивается **по конкретному вызову, а не по подкоманде**.

| Категория | Вердикт | Причина |
|---|---|---|
| Read-only командлеты PowerShell (`Get-ChildItem`, `Get-Content`, `Select-String`, `Test-Path`) | Можно | Флагов записи не существует |
| Точный вызов скрипта проверок (`Bash(npm run typecheck)`) | Можно | Одна конкретная строка |
| `git log:*`, `git diff:*`, `git show:*` | **Нельзя** | `--output=ФАЙЛ` пишет произвольные файлы. Вдобавок избыточно — см. ниже |
| `npm run:*`, `make:*`, `cargo run:*` | **Нельзя** | Запуск любого скрипта = произвольный код |
| `node:*`, `python:*`, `npx:*`, `bunx:*` | **Нельзя** | Интерпретаторы и раннеры пакетов |
| `git fetch:*`, `git pull:*` | **Нельзя** | `--upload-pack=<cmd>`, remote вида `ext::` исполняют команду |
| `gh api:*` | **Нельзя** | «Только GET» префиксом не выражается |
| `curl:*`, `wget:*` | **Нельзя** | Умеют POST — канал утечки |
| Правило с пайпом, редиректом, `-c key=value`, `VAR=x cmd` | **Нельзя** | Выглядит read-only, а исполняет или пишет |

### Избыточные правила — отдельная ловушка

Claude Code сам, без всяких правил, разрешает read-only команды с проверкой флагов: `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `find`, `diff`, `which`, `echo`, `sort`, `jq`, read-only подкоманды `git` (`status`, `log`, `diff`, `show`, `blame`, `branch`, `ls-files`, `rev-parse`, …), read-only подкоманды `gh` (`pr view`, `pr list`, `run view`, …), `docker ps` / `images` / `logs` / `inspect`.

Правило на такую команду **не убирает ни одного подтверждения** — оно только снимает проверку флагов, которая работала. `Bash(git log:*)` — чистый минус: пользы ноль, `--output=` открыт.

Практическое следствие: git запускать через инструмент Bash, а не через PowerShell — там read-only подкоманды разрешены автоматически и с валидацией.

## Как замерить у себя

Транскрипты лежат в `~/.claude/projects/<encoded-cwd>/*.jsonl`, по одному JSON-объекту на строку. Вызовы инструментов — это `assistant`-сообщения с элементами `message.content[]` типа `tool_use`; для shell-команды строка лежит в `input.command`.

```powershell
$root  = "$env:USERPROFILE\.claude\projects"
$files = Get-ChildItem $root -Filter *.jsonl -Recurse -File |
         Where-Object { $_.Name -ne 'journal.jsonl' } |
         Sort-Object LastWriteTime -Descending | Select-Object -First 50

$shapes = @{}; $heads = @{}
foreach ($f in $files) {
    foreach ($line in [System.IO.File]::ReadAllLines($f.FullName)) {
        if ($line -notmatch '"tool_use"') { continue }
        try { $o = $line | ConvertFrom-Json } catch { continue }
        foreach ($item in $o.message.content) {
            if ($item.type -ne 'tool_use') { continue }
            if ($item.name -notin @('Bash','PowerShell')) { continue }
            $cmd = $item.input.command; if (-not $cmd) { continue }

            $shape = if ($cmd -match '^\s*(\$|foreach|if\s*\(|for\s*\()') { 'SCRIPT' }
                     elseif ($cmd -match '(&&|\|\||;|\s\|\s)')            { 'COMPOUND' }
                     else                                                 { 'SIMPLE' }
            $sk = "$($item.name)|$shape"
            if (-not $shapes.ContainsKey($sk)) { $shapes[$sk] = 0 }
            $shapes[$sk]++

            $first = ([regex]::Split($cmd, '\s*(?:&&|\|\||;)\s*'))[0].Trim()
            if (-not $heads.ContainsKey($first)) { $heads[$first] = 0 }
            $heads[$first]++
        }
    }
}
"-- формы вызовов --"
$shapes.GetEnumerator() | Sort-Object Value -Descending | ForEach-Object { "{0,5}  {1}" -f $_.Value, $_.Key }
"-- повторяющиеся строки целиком --"
$heads.GetEnumerator() | Where-Object { $_.Value -ge 3 } | Sort-Object Value -Descending |
    Select-Object -First 20 | ForEach-Object { "{0,5}  {1}" -f $_.Value, $_.Key }
```

Читать результат так:

- **Много `SCRIPT` / `COMPOUND`** — правила почти не помогут, работай по шагу 1 (сменить инструмент).
- **Есть строки с повтором ≥ 3** — вот кандидаты в точные правила.
- **Одна и та же команда в разных формах** — кандидат на стандартизацию по шагу 2.

Считать вызовы `Edit` и `Write` тоже стоит: обычно это крупнейшая группа, и закрывается она одним `defaultMode: acceptEdits`, а не списком правил.

### Две ловушки замера на Windows

- **Подтверждённые запросы в транскрипте не отмечаются** — видно только отклонённые (`toolDenialKind`). Поэтому считается не «сколько раз спросили», а «сколько вызовов не покрыто правилом».
- **PowerShell 5.1 читает `.ps1` как ANSI.** Скрипт замера, сохранённый в UTF-8 без BOM, ломается на не-ASCII символах: длинное тире превращается в `вЂ”`, где `”` — типографская кавычка, а её PowerShell считает закрывающей кавычкой строки. Дальше парсер сыплется в непредсказуемом месте. Держи такие скрипты в чистом ASCII либо сохраняй с BOM.
